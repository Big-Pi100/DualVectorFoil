> **一句话总判断：A 不是垃圾项目，是坏模板——内容扎实、架构为零。它的价值是反面样本，不是设计参照。**

### 1.2 它的三层结构（可直接对照我们的管线）

```
levels/LevelFactory.gd        ← 关卡图：23 个节点，带世界地图坐标 + require 锁钥
      ↓
levels/LocationFactory.gd     ← 区域表：18 个区域，每个指向 levels/<area>/0-0.tscn
      ↓
levels/<area>/<列>-<序>.tscn  ← 房间块：一个 TileMap + 物件实例（梯子/闸门/水/尖刺/传送点）
```

关键观察（读源码确认）：

- **房间块命名是「列-序」**：`aquaduct` 有 `0-0..0-9`、`1-0`、`2-0..2-3`。名字像网格坐标，但**邻接不靠名字**。
- **邻接靠场景里的 `Teleport` 节点**：`0-0.tscn` 的传送点指向 `0-1.tscn` 和 `2-3.tscn`。也就是说**房间图是硬编码在场景里的，不是数据驱动的**。
- 每个房间自己有边界：`boundaries/NW` 与 `boundaries/SE` 两个 `Position2D`（例：`(-646,-1702)` ~ `(426,234)`）。
- 关卡语义分四类：`quest`（拿道具）、`boss`、`bonus`（限时/计数）、`colosseum`（波次）。`Level.gd` 里还有 `sealdlevel`（阳光下无效的层）、`tint`、`mapid`。

## 2 仓库 B：sotnrando（月下夜想曲完整数据）

`https://github.com/sotnrando/sotnrando` · **WTFPL** · 最后提交 2026-11-27（活跃）

### 2.1 本地实测

| 文件 | 体积 | 内容 | 条目数（`name:` 计数） |
|---|---|---|---|
| `src/items.js` | 227 KB | 每件道具：类型、id、在哪些 zone、哪些实体 ID、蜡烛 ID | **277** |
| `src/enemies.js` | 91 KB | 敌人：属性、掉落、出现区域 | **411** |
| `src/stats.js` | 107 KB | 属性成长/等级表 | **254** |
| `src/equipment.js` | 169 KB | 装备（按槽位/攻防） | — |
| `src/relics.js` | 27 KB | 魔导器（能力解锁） | **35** |
| `src/cutscenes.json` | 1.1 MB | 剧情文本/触发 | — |
| `src/util.js` | 469 KB | 房间/地图/精灵偏移表（`offset` 出现 6632 次） | — |

`items.js` 的真实结构（原样）：

```js
{
  name: 'Heart',
  type: TYPE.HEART,
  id: 0,
  tiles: [{
    zones: [ ZONE.ST0 ],
    entities: [ 0x26e0, 0x28de ],
    candle: 0x30,
  }, ...]
}
```

这就是「**道具 → 区域 → 实体 ID → 蜡烛**」四级投放表。我们要做「哪个房间放什么」，可以直接借这个模型，不必自己发明字段。

### 2.2 它不能给你什么

- **没有美术**（不是资源库，是数据表）。
- **不能独立运行**：它是给原版 ROM 打补丁的随机器，必须有 SotN 镜像。
- 数据描述的是 Konami 的游戏内容，**数值可参考，成体系的照搬有版权风险**（WTFPL 只覆盖代码）。

## 3 两个仓库与我们工程的对照

| 我们的东西 | 仓库 A 对应物 | 差距 |
|---|---|---|
| `level_01.graph`（文本图 + after/below） | `levels/LevelFactory.gd`（23 节点 + require） | 它有**锁钥语义**（require 前置关卡），我们没有；它的 `position` 只是**地图 UI 上的图标坐标**，不是房间摆位 |
| `blueprints/*.txt`（ASCII 零件） | `levels/<area>/<列>-<序>.tscn`（TileMap） | 它是二进制/文本场景，我们是纯字符；它可视化，我们不可视化 |
| `gen_level.py` 拼装 + `layout.json` | 无对应物（**房间图硬编码在 Teleport 里**） | 我们比它高一层：我们有生成器且摆位是数据，它是手摆且摆位是场景引用 |
| `branch` 支线 | bonus / colosseum 关卡 | 它是「独立关卡」，我们是「同房间口袋」 |
| 敌人/道具表 | 仓库 B 的 items/enemies/stats | 我们只有 59 只敌人的摆放，没有数值表 |

**结论：A 补「内容体量」，不补「空间组织」——它恰恰是「有内容、没空间组织」的样本；B 补「数值与投放」；两者都不补「生成算法」。**

## 4 怎么用（三步，都不动现有代码）

1. **先玩**：下 Release v1.0.0 的 win-x64 包（约 27 MB，2022-05-05 打包，与最后提交同日）。⚠️ 源码本身是 Godot **3.x**（`config_version=3`、`PoolIntArray`、单节点 `TileMap`），4.x 打开会要求转换且丢瓦片；**只能跑打包版，不要试图用 4.x 开源码**。
2. **看体量**：264 间 / 15 个区域 / 32.8 万格瓦片 / 622 条 teleport 边 —— 这是「一个完整 SOTN 复刻要有多少内容」的实测答案，对我们只有量级意义。**不要拿它的尺寸分位数校准我们的常数**，理由见 §4.2。
3. **后借**：只借两样——`Level.gd` 的关卡字段设计（quest/boss/bonus + require + reward + item）和 B 的投放表结构。**代码与贴图不整包引入**，避开 GPL/CC-BY-SA。

### 4.1 它到底是什么（实测定性）

**不是垃圾项目，是坏模板。**

- 它不是垃圾：264 间房的 `boundaries` 规整吸附在 16px 象限网格上（149 间两边半格、91 间两边整格、其余 24 间），327,873 格瓦片、729 张 PNG、52 个音频、23 个关卡节点、21 条 require 边、有存档系统、有可执行 Release。一个人做的完整 SOTN 复刻，2022-05 停更至今。
- 它是坏模板：**它是一堆内容，不是一个系统。** 没有生成、没有校验、没有全局摆位。空间关系不是数据，是 622 条 `Teleport` 节点的 `position + target_level` 引用。

### 4.2 它不该被怎么用

| ❌ 错误用法 | 为什么错 |
|---|---|
| 拿它的房间尺寸校准我们「一间房多大」 | 血统不同。它是 SOTN（中位 1.5×1.6 屏、多屏卷动、一区 15~32 间），我们是 DC（一屏房、线性闯关、一关 9~12 间）。**坐标系不同，分位数没有可比性。** 26×15 格 ≈ 1 屏在 DC 里是正确的，不该按它的「第 9 百分位」往上调 |
| 把它当「房间怎么摆」的参考 | 它**没有全局摆位图**。`LevelFactory` 里的 `position` 是地图 UI 上的图标坐标，不是房间世界坐标。想还原整图得自己解 622 条 teleport 边的方程组，仓库没存这个答案 |
| 用「它没有生成器」判它没价值 | 维度错。它的定位是内容库，不是关卡系统。拿生成器的标准评内容库，等于拿锤子量水 |
| 整包引入代码或贴图 | 代码 GPL-3.0 有传染性、美术 CC-BY-SA 需同协议分发，都不能进商业项目 |

### 4.3 它真正值的那一条

**反面样本：不做摆位数据化的终局，是 264 个孤岛。**

它把房间做成了独立场景、用场景内的 teleport 互相指认——这条路的尽头就是「房间之间没有地图，只有引用」。这正是 `layout.json` 必须存在、且摆位必须是**数据**而不是**场景引用**的理由。这一条比任何尺寸数据都有价值。

实测尺寸分布留档（仅作量级参考，**不参与设计决策**）：

| 项 | 264 间网格房实测 |
|---|---|
| 宽 | 中位 38.5 格（1.5 屏），p25 26.5 / p75 60.5 / max 143.5 |
| 高 | 中位 30.0 格（1.6 屏），p25 22.5 / p75 48.0 / max 116.5 |
| 面积 | 中位 1,241 格² |
| 每区房间数 | 15 区，9~32 间，平均 17.6 |
