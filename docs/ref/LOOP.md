# 月下主循环（RicMain）逐行拆解

> 数据来源：`research/mv/sotn_src/`（sotn-decomp，AGPL-3.0-or-later）。
> 只读、只提炼结构与数值，不复制代码。
>
> **这一版之前，我的主循环是"我觉得顺"的顺序排的垃圾。**
> 症状：按 J 有动画有声音但永远打不到东西；按 K 会同时起跳；
> 攻击中还能转身、能跳、能施法；站着不动会莫名其妙掉进 fall。
> 根因全在下面这几段里。

## 一、RicMain 的顺序（`pl_main.c:397`）

```
RicMain()
├─ 1. 所有 timer 递减          for (i=0; i<LEN(timers); i++) if (--timers[i] == 0) ...
├─ 2. 读输入三态              padHeld = 上帧; padPressed = 本帧; padTapped = 异或
├─ 3. 受伤检测                 hitParams != 0 → RicSetStep(PL_S_HIT)   ← 在 step 分派之前
├─ 4. prev_step = step
├─ 5. step 分派                switch (step) { case PL_S_STAND: RicStepStand(); ... }
├─ 6. status 标志              由 step 反推：无敌 / 蹲 / 副武器 / 施法中
├─ 7. UpdateAnim               推进动画帧（在物理之前！）
├─ 8. 清 hitParams = 0
└─ 9. 物理位移 + 碰撞
      if (|vx| > 2px/帧 || |vy| > 2px/帧) {
          vx >>= 2; vy >>= 2;
          CheckStageCollision ×4        ← 分 4 个子步
          vx *= 4; vy *= 4;
      } else CheckStageCollision ×1;
```

### 三个反直觉的点

1. **动画在物理之前推进。** `UpdateAnim` 在位移之前，所以"这一帧画哪一帧姿态"和"这一帧走多远"是解耦的。
2. **物理是统一做的。** 状态函数只改 `velocityX/velocityY`，**从不碰 posX/posY**。这是整个架构最硬的一条规矩。
3. **高速时分 4 子步。** 最高 7px/帧（FIX(7)），一次走完会穿过 1 格厚的墙。

## 二、输入三态（`pl_main.c:499-513`）

```c
g_Player.padHeld    = g_Player.padPressed;              // 上一帧
g_Player.padPressed = g_pads[0].pressed;                // 本帧
g_Player.padTapped  = g_Player.padPressed & (g_Player.padHeld ^ g_Player.padPressed);
```

| 量 | 含义 | 用在哪 |
|---|---|---|
| `padHeld` | 上一帧按着 | 判断"上一帧就在按"（连招窗口） |
| `padPressed` | 现在按着 | **按住跳键才跳得高**、按住方向才走 |
| `padTapped` | **本帧新按下** | 出招、起跳、施法 |

混用的后果（我都踩过）：
- 用 `pressed` 判出招 → 按住攻击键每帧重复出招
- 用 `tapped` 判"按住跳更高" → 只有第一帧算，之后都当没按

**我们的等价实现**：`keys`（现在按着）+ `taps`（本帧新按下，帧末清空）。
没用 `prevKeys` 异或，因为在无头测试里"同一帧按下又松开"会丢事件 —— `taps` 保留这一类，语义更稳。

## 三、RicCheckInput —— 输入分发的单一入口（`pl_collision.c:4`）

每个状态函数的第一件事都是它：

```c
void RicStepStand(void) {
    if (!RicCheckInput(CHECK_FALL | CHECK_FACING | CHECK_JUMP | CHECK_CRASH |
                       CHECK_ATTACK | CHECK_CROUCH | CHECK_SLIDE)) {
        RicDecelerateX(FIX(0.125));      // ← 只有"没被消费"时才做本状态的默认行为
        ...
    }
}
```

返回值 = **这次输入被本状态消费了**。调用方据此决定要不要执行默认行为。

### 内部顺序（不能改）

```
1. CHECK_FACING   → 转身（但 g_Player.unk46 == 0 才转，即攻击锁里不转身）
2. CHECK_GRAVITY_* → **加重力**（见下节，这是最反直觉的）
3. clamp velocityY ≤ FIX(7) = 7px/帧
4. CHECK_80 + 撞顶 → velocityY = FIX(-1)
5. velocityY >= 0 && CHECK_GROUND && 触地 → 落地处理，return true
6. CHECK_FALL && 离地 → RicSetFall()，return true
7. ★ if (unk46 != 0) return false;        ← **攻击锁：屏蔽一切后续输入**
8. CHECK_CRASH   → △ 副武器/大招
9. CHECK_SLIDE   → ↓ + ×（蹲着时按跳 = 滑铲）
10. CHECK_JUMP   → ×
11. CHECK_ATTACK → □ 攻击
12. CHECK_CROUCH → ↓ 蹲
```

### 各状态允许的输入集

| 状态 | 传入的 checks | 说明 |
|---|---|---|
| Stand | FALL, FACING, JUMP, CRASH, ATTACK, CROUCH, SLIDE | **不含 GROUND** —— 站着时不该反复进"落地"分支 |
| Walk | FALL, FACING, JUMP, CRASH, ATTACK, CROUCH | 不含 SLIDE |
| Jump | **GROUND**, FACING, ATTACK, **GRAVITY_JUMP** | 不含 JUMP —— 空中跳在函数体里单独判 |
| Fall | **GROUND**, FACING, ATTACK, **GRAVITY_FALL** | 同上 |
| Crouch | FALL, FACING, ATTACK, SLIDE | 蹲跳/滑铲在函数体里单独判 |
| Hit | GRAVITY_HIT, GROUND_AFTER_HIT | 硬直里不能操作 |

**这是我最初搞错的地方**：Stand 不传 GROUND。传了的话，站着时每帧都会命中"落地"分支并 `return true`，后面的攻击/跳/蹲判定永远执行不到 —— 表现就是"按键没反应"。

## 四、重力是"申请"的，不是独立阶段

三种档位，值不同：

| 标志 | 触发条件 | 值 | 出处 |
|---|---|---|---|
| `GRAVITY_FALL` | 下落 | `FIX(28/128)` = 0.21875 px/帧² | `pl_collision.c:14` |
| `GRAVITY_JUMP` | 上升 | 0.21875，**但顶点窗口内 ×1/5** | `pl_collision.c:17-26` |
| `GRAVITY_HIT` | 受击浮空 | 顶点窗口内 ×1/2 | `pl_collision.c:27-34` |

### 顶点窗口是非对称的

```c
if (PLAYER.velocityY < FIX(3.0/8) && PLAYER.velocityY > FIX(-1.0/8) &&
    !(g_Player.unk44 & 0x20) &&            // 这一跳没撞过顶
    (g_Player.padPressed & PAD_CROSS)) {   // **按住**跳键
    velYChange = FIX(5.6/128);             // 28/5 = 5.6，正好 1/5
}
```

换算到我们的尺度（×3 格，px/帧 → px/s 乘 60×3）：

| 量 | 原版 | 我们 |
|---|---|---|
| 重力 | 0.21875 px/帧² | 2362 px/s² |
| 顶点窗口 | **-0.125 ~ +0.375** px/帧 | **-22.5 ~ +67.5** px/s |
| 窗口内重力 | 1/5 | ×0.2 |
| 终速 | 7 px/帧 | 1260 px/s |
| 撞顶 | -0.25 ~ -1 px/帧 | -45 px/s |

**关键**：窗口是 `-1/8 ~ +3/8`，不是对称的 ±某个值。我原来写的 `Math.abs(vy) < 120` 既对称又太宽，等于凭空造了一个"顶点滞空"，不是原版的。

> 这条机制让全程滞空从理论的 829ms 变成实测 983ms。**多出来的 154ms 就是顶点窗口**，不是 bug。

## 五、各状态做了什么（`pl_steps.c`）

### 恒速 ≠ 没有摩擦

```c
void RicStepWalk(void) {
    if (!RicCheckInput(...)) {
        RicDecelerateX(FIX(0.125));     // 先减
        ...
        RicSetSpeedX(FIX(1.25));        // 再重设
    }
}
```

**每帧先减速再重设**，所以看起来是恒速 1.25。但一松开方向键就切到 Stand，那边**只减速不重设** → 滑行 10 帧、约 29px 才停。

我上一版把 `FRIC_G` 设成 `1e6`（瞬停）—— 把最像恶魔城的滑行抹掉了。

### 跳

```c
void RicStepJump(void) {
    // 松手切断：绝对值，不是乘系数
    if (PLAYER.velocityY < FIX(-1) && !(padPressed & PAD_CROSS))
        PLAYER.velocityY = FIX(-1);
    // 撞顶
    if (TOUCHING_CEILING && velocityY < FIX(-1))
        velocityY = FIX(-0.25), unk44 |= 0x20;
    if (RicCheckInput(CHECK_GROUND | CHECK_FACING | CHECK_ATTACK | CHECK_GRAVITY_JUMP)) return;
    ...
}
```

### 二段跳（其实是"空中跳"）

在 `RicStepFall` 的 `step_s == 0` 分支里：

```c
if (g_Player.timers[PL_T_5] && g_Player.padTapped & PAD_CROSS)
    RicSetJump();
```

由 timer 控制次数，不是"能力开关"。我们的等价物是 `SAVE.owned.has('djump')`。

### 攻击

不是"状态里播个动画"，是**生成一个独立实体**：

```c
// RicStepStand, step_s == 64
if (g_Player.padPressed & PAD_SQUARE) {
    PLAYER.step_s++;
    g_Player.unk46 = 2;                                   // ← 攻击锁
    RicSetAnimation(ric_anim_brandish_whip);
    RicCreateEntFactoryFromEntity(g_CurrentEntity, BP_ARM_BRANDISH_WHIP, 0);
}
```

`BP_ARM_BRANDISH_WHIP` 在 `pl_whip.c:496` 逐帧查表：

```c
D_80155CB8[] = { 10, 11, 13, 17, 15, 12, 18, 14, 16 };   // 9 帧 × 9 个方向
```

蹲下和空中各有一张不同的表。**攻击的实际帧数是 9 帧（150ms）**，判定框跟着手臂姿态走。

### 受击

```c
ric_hit_stun_timer = 0x18;    // 24 帧 = 400ms
func_8015CAAC(FIX(-1.25));    // 水平击退
PLAYER.velocityY = FIX(-3);   // 垂直击飞
```

- **9 方向挥鞭姿态表**：需要 ROM 里的手臂帧图，我没有。

所以对外只能说：**移动、跳跃、受击、攻击时序的 loop 结构和数值对齐了；动画与判定精度没对齐。**

## 八、踩过的坑（都在这一版修掉）

1. **攻击判定框在 `y+8 ~ y+52`**，敌人站在 `y+62 ~ y+100` → 垂直永不重叠 → 按 J 有动画有声音，打不到任何东西。
2. **`stepCrouch` 没走 `checkInput`** → 蹲下后所有输入被吞，站不起来。
3. **`stepJump` 没带 `CK.JUMP`** → 空中跳（二段跳）永远触发不了。
4. **`↑` 被映射成跳** → 原版是 `press_up`（抬头）。跳是 `×`。
5. **蓝魂键发 `'k'`**，而跳键别名里有 `'k'` → 手机按蓝魂会同时起跳。
6. **站立时不加重力**，physics 用"位移有没有被挡住"判落地 → `dy=0` 时误判"脚下是空的" → 掉进 fall。必须用**地面传感器**（原版是 `vram_flag & TOUCHING_GROUND`）。
7. **`prevKeys` 异或**在无头测试里丢事件（keyup 不经过帧）→ 连续按键失效。改用 `taps` 事件记录。

## 九、反馈层：键通了 ≠ 玩家知道（这一轮的全部发现）

白哥原话：「除了方向以外其他按钮都没有任何反馈（而且会卡住）—— 也可能不是没效果，只是画面没反馈？
这个要你调查。下可以蹲，但是下加空格就是闪烁。行走的时候人物就不见了」

我先按"逻辑没触发"去查，结果**每个键的状态机都跑对了**（`state()` 一个个验的：attack / cast / crouch / slide 全都在）。
问题全在**画面上没说话**。这一类 bug 测试抓不到 —— 逻辑测试只看状态，不看像素。

### 1. 走路时人物消失（不是状态坏了，是一帧都没画）

`PACK_ATLAS.map.walk = 'walk'`，而名片管线只导出 `idle / wave / attack / kick / hit` 五组。
`animFrames('walk')` 返回空数组 → `drawAtlasFrame` 在 `if (!frames.length) return` 直接退出 → **整个人不画**。

阴在：站着正常、跳正常、攻击正常，只有走的时候没有 —— 看起来像"走路状态坏了"，其实是素材键写错。
**改法**：`walk → 'idle'` + 程序化步态（见第 4 条）。**判据**：`map` 里的每个值都必须能在 `animations` 里查到。

### 2. 下+空格 = 闪烁（状态机里有"过路状态"）

`stepSlide` 收势统一回 `stand`，下一帧 `checkInput` 又因为 ↓ 还按着转成 `crouch`。
压缩值 0.52 → 1.0 → 0.66 三帧跳两下 = 闪。
**改法**：收势直接落到"下一帧本来就在的状态"，`↓ 还按着 → crouch`。状态机不该经过一个马上就会离开的状态。

### 3. 蹲着按方向 → 人原地抖、走不动（两个状态互相设回来）

`stepCrouch` 见方向 → 起身 → `stepStand` 的 `checkInput` 见 ↓ → 蹲下 → 循环。
每帧 stand/crouch 交替，`P.vx` 被 `crouch` 每帧清零 → **读起来就是"按了↓之后卡住了"**。
**改法**：`checkInput` 的 CROUCH 分支里，按着方向就不进蹲（"想走就别蹲"）。这是白哥说的"卡住"的主因。

### 4. 走路读不出"在走"（素材缺帧时的唯一诚实办法）

只有 4 帧 idle，硬画会像"滑行"。补三层都由**走过的距离**驱动（不是时间）：
- `P.walkPhase += |vx|·dt / 31`（半步 31px，225px/s ≈ 3.6 步/秒）
- 躯干上下颠 ±4px、左右摆 ±5°、两拍一次 ±1.8% 压缩
- 一脚两粒土（`stepT > 62px` 触发）

距离驱动而不是时间驱动：停下相位就不动，不会在原地虚空踏步。
另加 `P.walkW`（0..1 权重）平滑起停 —— 否则停在 sin 峰值时人会悬空 4px 站着。

### 5. `↑` 抬头完全没有视觉表达

`P.lookUp` 只被赋值、**从来没有被渲染读过**。玩家按 ↑ 屏幕上零变化 = "键坏了"。
**改法**：抬头时镜头往上让 84px（原版 `ric_anim_press_up` 就是"看上方"）。
踩到的第二个坑：纵向死区 62px 比抬头位移还大 → `camY` 一格都不动。抬头时必须同时把死区收到 18px。

### 6. 攻击"看不出在打"（这一条最关键）

照片管线生成的 attack 4 帧**姿态差异极小**（真人照片本来就动不了），精灵帧本身传达不了"我在出招"。
**改法**：加挥击弧 —— 三道同心弧 0.26s 扫过身前（`particles.push({arc:true, noGrav:true, ...})`）。
两道坎：
- 第一版半径只有 30~50，弧整个落在人物轮廓里，被精灵自己的像素吃掉 → 中心要放到**身前**、半径压到轮廓外。
- 弧的最内层是纯白，叠在冷色暗底上会变成**近灰**（叠加后 `b-r ≈ 1`），任何"偏蓝"的判据都会漏掉它；
  反过来偏蓝的外层又太淡够不到亮度阈值 —— 所以验证只能用"全画面最大亮度和"（648 → 694）。

### 7. 蓝魂没装备时按下去零回应

`equipped.blue` 为空时 `gliding` 恒 false，按 I 什么都不会发生。**加一句 `say(...)` 就够了。**

### 8. 姿态压缩用 `Math.min` 硬切 = 抖动之源

原来渲染里 `sq = Math.min(sq, 0.66)`，状态一变压缩瞬间跳到位。
**改法**：状态只写目标 `P.poseSq`，`P.sq` 每帧 `+= (target - sq) · min(1, dt·22)` 追过去。
蹲/滑铲/起跳拉伸共用一条曲线，任何切换都连续。

### 这一轮的教训

- **"没反馈"要先分两类**：状态没变（逻辑 bug）／状态变了但画面没变（表达 bug）。上一轮我两次都只测了前一类。
- **判据要按真实叠加后的像素定**，不能按源码里的颜色值定。`#eaf8ff` 叠在暗紫上不是 `#eaf8ff`。
- **截图不能当"看得见"的证据**：`page.screenshot()` 本身要几百毫秒，0.2s 的特效早没了。
  要证明"画出来了"，必须在页面内逐帧取像素或数绘制调用。

## 十、键位：原版只有两个动作键（这一轮重做）

### 先把原版读准

AoS 的物理键一共六个，但**动作只占两个**。剩下四个里，两个是"修饰"，两个是系统键：

| GBA | 功能 | 是不是独立动作 |
|---|---|---|
| ← → | 移动 | — |
| ↓ | 蹲 | — |
| ↑ | 抬头 / 对话 / 进门 / 存档 | — |
| **A** | 跳（按住更久跳更高） | ✅ 独立动作 |
| **B** | 攻击 | ✅ 独立动作 |
| **↑ + B** | 红魂（Bullet Soul） | ❌ B 的**组合** |
| **↓ + A** | 滑铲 | ❌ A 的组合 |
| **↓ + B** | 从薄地板掉下去 | ❌ B 的组合 |
| **A × 2** | 二段跳 | ❌ A 的连按 |
| **R** | 蓝魂（Guardian），按住持续 | ✅ 独立（唯一"按住型"） |
| **L** | 能力键（Grave Keeper 的后跃） | ✅ 独立（低频） |
| START | 状态菜单 | 系统 |
| SELECT | 地图 | 系统 |

**这就是原版的按键哲学：动作键越少越好，其余全靠方向修饰。**
所以 A→跳、B→攻 两根手指就能打完整个游戏，魔法是"按上再按 B"。

上一版我们犯了什么错：把红魂做成了第三个独立攻击键（`L`）。
表面看更省事，实际把原版最核心的一条设计丢了 —— **方向是动词的一部分**。
玩家按住 ↑ 想打头顶的敌人，原版放魔法，我们什么都不放（因为没实现"上攻击"）。

### 现在的键位

```
         W                    J  K  L
      A  S  D                 U  I  O
```

| 动作 | 键 | 原版对应 |
|---|---|---|
| 攻击 | **J** | B |
| 红魂 | **U** 或 **W + J** | ↑ + B（两套都留：U 是便捷键，W+J 是原版语义） |
| 跳跃 | **K** 或 空格 | A |
| 后跃 | **I** | L（能力键） |
| 蓝魂 | **L**（按住） | R |
| 魂匣 | **O** / Tab | START |
| 滑铲 | **S + K** | ↓ + A |
| 穿板 | **S + J**（站在薄板上） | ↓ + B |
| 蹲 | **S** | ↓ |
| 抬头 | **W**（只动镜头，不移动） | ↑ |
| 静音 / 重开 | M / R 连按两次 | — |

**为什么是 J K L / U I O 而不是别的排法** —— 不是"手够得着"，是让**同一个手指管一对语义**：

| 手指 | 上排 | 下排 | 这一对在说什么 |
|---|---|---|---|
| 食指 | J 攻击 | U 红魂 | 打出去：物理 / 魔法 |
| 中指 | K 跳 | I 后跃 | 位移：向前 / 向后 |
| 无名指 | L 蓝魂 | O 魂匣 | 状态：按住的能力 / 系统 |

上一版 `J 攻 / K 跳 / L 红 / I 蓝` 能被按到，但**没有分组逻辑**，玩家记不住
"蓝魂为什么在食指下排"。键位表能背下来，靠的从来不是位置，是关系。

### 手机端

右手只有一根拇指，所以**不能照搬六个键**。按 AoS 的"主次"来排：

```
              [后 52]
        [红 64]  [蓝 64]
   [攻 80]              [跳 92]      ← 拇指落点，最大
```

- **跳**最大、最靠右下角（拇指的自然支点）—— 这是唯一一个"每两秒就要按一次"的键
- **攻**在左侧，用拇指根部够
- 红/蓝在上面一排，用指腹上挑
- **后**最小、最高（低频）
- **魂匣**挪到右上角 —— 系统键混在动作区里，按"跳"一定会蹭到；
  放顶部正中又会压住 `say()` 那行字幕（字幕画在 canvas 上，DOM 躲不开）

左手：浮动摇杆，左右移动、下推蹲（+跳=滑铲、+攻击=穿板）、**上推抬头**。

> 上推这一路以前是空的：手机上永远做不出抬头，等于把原版的一个方向位整个砍掉。

### 这一轮修掉的按键 bug

1. **R 在开局 1.6 秒内会直接重开。** 判断"两次连按"用的是 `now - reloadArm < 1600`，
   而 `reloadArm` 初值是 0 —— 页面刚加载时 `performance.now()` 本来就小于 1600，
   于是第一次按就被判成"第二次"。加一个 `reloadArm &&` 前置条件。
   这条是 `keymap_check.js` 抓到的：测试把"按 R 前后人物的 x 坐标"当判据，
   结果 x 从 444 跳回初始 336 —— 页面真的被刷了。
2. **手机端按键键名和键盘脱节。** 键盘上 `l` 从红魂改成蓝魂之后，
   手机端还发着 `l` —— 按"蓝"会放红魂。这类错位桌面上永远测不出来，
   只有在真机点按钮才露。现在两边共用同一份主键名，注释里写死对照。
3. **手机端上推没有映射**（见上）。
4. **按住 Tab / O 会疯狂开关菜单**：系统按键重复（500ms 后每 30ms 一次 keydown）
   没有挡。加 `!e.repeat`。
5. **`held` / `tapped` 两个死函数**引用了一个已经不存在的 `prevKeys`。
   没人调用所以不报错 —— 这种代码下次一定有人拿来用，删掉。

### 新增的验证脚本：`keymap_check.js`

`test.js` 在 vm 里直接调 `key()`，它证明的是"逻辑分支通"，证明不了
"按下这个物理键，游戏里发生的事和说明书一致"。键位是一张**映射表**，
映射错了 vm 全绿、玩家全懵。

所以这个脚本只做四件事（真 Chromium + 真键盘事件）：
- **A** 每个动作键 → 状态真的变了（D/A/W/S/J/K/U/I/L 各一条）
- **B** 组合键走的是组合分支：`↑+J` 必须是魔法、裸 `J` 必须是普攻
- **C** 危险键：`R` 按一次不许重开；`O` 开关菜单
- **D** 手机层，两小步：
  1. **几何**：六个按钮的 `getBoundingClientRect()` **两两不重叠**、都在屏内、
     最小边 ≥44px（苹果 HIG 的触控下限）
  2. **按得动**：用真指针事件按下去，看 `state()` 变没变（跳→jump、攻→attack、
     后跃→dash、摇杆右拖→walk、下拖→crouch）

> 第 2 步不能省。只量矩形的话：位置完美、事件其实没绑上，测试照样全绿、
> 玩家照样点不动。**几何正确 ≠ 可用。**
>
> 几何那一项是唯一能自动发现"按钮摞在一起"的办法。肉眼看截图只能看见明显的重叠，
> 8px 的擦边根本看不出来 —— 而那 8px 就是"按跳的时候蹭到蓝魂"。
