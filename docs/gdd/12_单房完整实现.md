# 12 · 一间房的完整实现（Room01）

> 建 2026-11-27。**这份取代 `10_垂直切片` 的范围定义。**
> `10` 的 §3.0 实施记录（S0/S1/S2）仍然有效，作为历史留档；但它「5 间房 + 2 能力 + 1 Boss」
> 的范围**作废**。

---

## 0. 为什么重写计划

白哥的判断：**「一个房间还没有搞好，就一次搞这么多房间，有什么意义吗？」**

这是对的，而且比表面上更严重。逐条对账：

| 我做过的事 | 我以为的成果 | 实际情况 |
|---|---|---|
| S0 敌人 AI | 「敌人会打人了，V1 成立」 | V1 只在一个**手动塞了 `invaded_rooms` 的测试**里成立 |
| S1 玩家会死 | 「站门口 15.9 秒会死」 | 同上。**真实开局进 Room01 是空房，一只敌人也没有** |
| S2 折叠上锁 | 「闭合了能力闭环」 | 闭的是 Room03 的环。Room01 自己还是一个空盒子 |
| 6 间房 + 蓝图生成器 | 「房间有空间设计了」 | 6 间房各有一点，**没有一间能从头玩到尾** |

**硬证据（2026-11-27 实测，`tools/_probe_fresh.gd`）**：

```
=== 全新存档进 Room01 ===
invaded_rooms = []
房间里敌人数量 = 0
容器可见 = false
```

根因：敌人只在 `WorldState._try_trigger_gentle_invasion()` 里生成，
而它的候选是「**已经种了作物**的房间」。种植是 P2 的东西。
**所以新玩家打开游戏，第一间房必须是空的。**

这就是「广度铺到 48 房、深度停在 0 房」的真实后果——
连唯一那间「教学房」，在真实开局里都没有内容。

## 1. 范围

**本轮只做 `Room01` 一间。**

| 类别 | 内容 |
|---|---|
| **在范围内** | `Room01` 的空间 / 敌人编成 / 教学 / 清场反馈 / 出口。<br>`SafeHouse` 只做**死亡落点**，不加任何新内容。 |
| **冻结（不碰）** | `Room02` `Room03` `Room04` `Room05`。冻结 = 不改一行，也不保证能玩。 |
| **明确不做** | 生长 / 投掷 / Boss / 种植玩法扩展 / 墙平台贴图 / 48 房拓扑 |

冻结的理由：`Room02` 现在也是空房，如果 `Room01` 做好而右门通向空房，
玩家的体验是**断的**。所以出口必须收在这间房自己身上（见 F5）——**这本身就是设计题，不是回避**。

## 2. 什么算「一间房完整」：90 秒时间线

判据不按模块列，按**玩家从进门到出门实际经历的顺序**列。缺任何一行，这间房就不完整。

| 时刻 | 玩家应该经历 | 现状 | 判据（可断言，不看感觉） |
|---|---|---|---|
| **0s 进门** | 一眼看见这间房的「形状」：哪边是死的、哪边要往上 | 一条平路，两级 96px 台阶可有可无 | 房间有 **≥3 个高度层**，且最高层与地面差 **> 单跳 211px** |
| **3s 知道按什么** | 不查攻略就知道能跳、能打 | **零提示** | 首次进入出现一次操作提示；按过之后**不再出现** |
| **5s 遇到敌人** | 进门就有人挡路 | **0 只**（见 §0） | 全新存档进房，敌人 **≥1 只** |
| **15s 被迫用跳** | 不跳就过不去 / 躲不掉 | 平路直通右门 | **不按跳跃，走不到右门**（只走平地的 BFS 不含右门） |
| **40s 打出结果** | 要么清场，要么死回暗房 | 打不了（空房） | 清场可达 / 死亡可达，两条都成立 |
| **清场瞬间** | 房间变了，而且**「所以我可以走了」** | 0.85s 波纹 + 紫月褪色，无功能意义 | 右门**由锁到开**（清场前不可通行） |
| **出门** | 知道这是这间房的终点 | 踩上去直接切场景 | 清场后才切场景；出门=本房完成 |

## 4. 已知的坑（从 S0–S2 带过来的）

| 坑 | 后果 | 应对 |
|---|---|---|
| `ws.set("invaded_rooms", [...])` 对 `Array[String]` 静默失败 | 测试报「没打到人」，其实是房间没入侵 | 必须 `(ws.get(...) as Array).append(...)` |
| `get("is_on_floor")` 返回 Callable 不是 bool | `== true` 永远 false | `p.call("is_on_floor")` |
| `get("velocity.y")` 永远 null | 拿不到速度 | `(p.get("velocity") as Vector2).y` |
| `--script` 入口脚本不能写 `WorldState.xxx` | 编译期 autoload 未注册 | `root.get_node("/root/WorldState").call(...)`，且先 `await process_frame` |
| Godot 4.7 无 `bool()` / `float()` 构造器 | Parse Error | 显式类型标注 |
| 触屏按钮在桌面也常显，盖掉右半屏 | 这间房「看不见」 | 按设备切换 HUD，或试玩时隐藏 |
| 断言绿但玩家玩不出来 | 空间/形变/位置问题只有截图能看出来 | 每步都实拍 |

## 7. 结构重做（第二次，2026-11-27 晚）

> ⚠️ **本节描述的版本已被否、已被 `§8` 覆盖。** 保留原因只有两条教训
> （`#` vs `=` 的区别、测试不能全程按住右），其余数值全部作废。

### 7.1 第一次为什么还不够

第一次重做把房间改成「地面 + 三级台阶（480 / 336 / 192）+ 三块 6 格台」。
它**过了当时全部判据**：4 个高度层、必跳 3 次、3 层敌人。

白哥原话：

> 「**你这还是连结构都没有任何可玩性。重生细胞人家的房间都可以随机生成，
> 你连一个房间都不会设计。什么时候这一个房间达到游戏水平，什么时候就别下一步。**」

问题不在「有没有层」，在**没有岔路**。
三级台阶只有一条上升路径：删掉任何一级，出口就断了。
玩家在里面只做一个动作——往右上爬。这就是「把走廊竖起来」，仍然是走廊。

**教训：判据「层数」和「跳数」抓不住「一条线」。** 它们只能证明「不是平地」，
证明不了「有选择」。要证明后者，得测**删掉一块之后还能不能出去**。

### 7.2 这一版的形状

```
C 层 y=192   c10-c15   c17-c21   c23-c24      出口层，右门在 c25
B 层 y=336   c6-c10    c12-c16                岔路层
壁龛 y=336   c1-c2                            支线，放 VistaPoint
A 层 y=480   c3-c7     c9-c13                 岔路层
地面 y=624   c1-c23                           右下 c24 是实心墙 → 死路
```

- **11 块平台**，每块 4–6 格，错开 1–2 格，不是连续台阶
- **两条路**（都是 3 跳）：
  - 路 1（左）：A1 → 壁龛(vista) → B1 → C1 → C2 → 门。顺路拿观景点，但 B1 有敌人
  - 路 2（右）：A1 → A2 → B2 → C2 → 门。一直往右更顺，没有敌人，但拿不到 vista
- **岔路口在 A1 右端**，E2 站在那儿 —— 先打完才轮得到选路
- **右下 c24 是墙**：地面走到 c23 就是死路，必须上楼。这是地形事实，不是猜的
- **地面 c13-c14 有 1 格凸起**：按住右不跳，连地面都走不完

### 7.3 五条新判据（全部进生成器，蓝图头声明）

| 键 | 阈值 | 抓什么 |
|---|---|---|
| `min_layers` | 4 | 一条平地 |
| `min_jump_to_exit` | 3 | 跳是装饰（0-1 BFS：上升边权 1，平移/下落 0） |
| **`min_alternate_stands`** | **6** | **楼梯房 —— 删掉整块平台后出口断掉** |
| `min_detour_stands` | 6 | 没有任何可选的去处 |
| `min_enemy_layers` | 3 | 敌人全在同一层对劈 |

第三条是这一轮的核心。**它换过两次定义才成立**，两次都是被反向验证打回来的：

| 定义 | 三级台阶的实测 | 为什么错 |
|---|---|---|
| 删掉一个**站面**，出口还可达 | 57 / 59 个「可绕」 | 地面有 24 格，删一格当然还有路 |
| 删掉一条**边**，出口还可达 | 18 个「分叉」 | A 台是 6 格连着的一条，封 A(c4)→B 还有 A(c5)→B |
| **删掉一整块平台**（同行相邻聚类），出口还可达 | **0** ✅ | 这才是「这块不要了，还能不能出门」 |

### 7.4 三条反向验证（全部 FAIL 到位）

| 故意改坏 | 命中判据 | 实测 |
|---|---|---|
| 换回三级台阶 | 岔路块 0 < 6 | `GEN ROOM: FAIL` |
| 敌人全塞到地面 | 敌人层 1 < 3 | `GEN ROOM: FAIL` |
| 只爬两层就到门 | 高度层 3 < 4、跳数 2 < 3 | `GEN ROOM: FAIL` ×3 |

> 顺带修掉一个**审计永远通过**的 bug：`--audit` 分支原本不看 `_fail`，
> 判据失败照样打印 `AUDIT: PASS` 并 `exit 0`。不修的话上面三条验证全是假绿。

### 7.5 这一轮最贵的坑：**实心台，玩家根本跳不上去**

这是「BFS 说能过、玩家过不去」的第二个实例（第一个是 S1 的血条）。

生成器的可达性验算认为三层台都能上，**实测三条上升跳全部失败**：

```
FAIL 地面(c2) → A1：落点 (270, 624)   还在原地
FAIL A1(c5)   → B1：落点 (414, 491)   卡在台边
FAIL B1(c9)   → C1：落点 (606, 336)   没上去
```

原因：三层台用的是实心 `#`。
玩家从下方跳上来，**先撞台底（只升 50px），再撞台侧面**，永远上不去。

修法：三层全改**单向平台 `=`**。玩家能从下方跳穿、落在顶面。

```
ok 地面(c2) → A1：落点 (280, 480)
ok A1(c5)   → B1：落点 (424, 336)
ok B1(c9)   → C1：落点 (616, 192)
ok C1(c15)  → C2：落点 (904, 192)   ← 跨 1 格缺口，会撞天花板，仍然过
```

判据落在 `tests/test_room01_traverse.gd`：真实物理帧，每条必须**站在目标台面 ±6px**，
掉回地面 / 卡在半空 / 撞墙掉下来都算 FAIL。

**两个衍生坑**：

1. **C 层 y=192 起跳会撞天花板**。天花板底 48，净空 144px，单跳要 204px。
   但撞完还能跨 1 格缺口：上升段 0.19s（+55px）+ 下落段 0.318s（+92px）
   = 147px ≈ 3 格。所以缺口从 2 格收到 **1 格**，给落点留余量。
2. **测试「全程按住右」会飞 5.5 格**（290 × 0.917s = 266px），
   越过 5 格宽的台落到台外。真人会在空中松手。
   测试必须模拟真人：助跑 10 帧 → 起跳 → 按住 20 帧 → 松开。

### 7.6 单向平台的视觉厚度 ≠ 碰撞厚度

改成 `=` 之后平台只剩 12px，实拍像「一根悬在空中的灰线」，读不出「这里能站」。
拆成两个常量：

- `PLATFORM_THICKNESS = 12`：碰撞（单向、可跳穿）
- `PLATFORM_VISUAL_H = 22` + 5px 顶面亮边：视觉

**两者本来就不必相等** —— 碰撞要薄，视觉要像台。

## 8. 第三次重做：判据整体反转（2026-11-27 深夜）—— **当前版本**

> ⚠️ **§7 已被本节覆盖。** §7 描述的是"错位网格 11 块台"那一版，
> 它同样被否了（白哥：「依然还是垃圾，你好好研究一下重生细胞的房间是怎么设计的」）。
> §7 保留下来是因为里面两条教训仍然成立：单向平台 `#` vs `=`、
> 测试不能"全程按住右"。其余结论（层数 4、必跳 3、岔路 6）**全部作废**。

### 8.1 根因：判据量错了东西

前一版 11 块台、4 层、3 次必跳、6 个岔路块 —— **判据全绿，玩家说垃圾**。
不是参数没调好，是**方向反了**：那组判据度量的是"跑酷难度"，
而 Dead Cells 的房间根本不是跑酷关卡。

依据 `docs/ref/REF_DEADCELLS_ROOM.md`：

> GDC 2019，Sebastien Bénard：
> *"Platforming is just a means to move, to avoid enemies, to position yourself,
> it's not a hardcore platformer game. ... Is the player meant to die doing this?
> If the answer is no, we just make sure the player succeeds."*

> Ars Technica War Stories：他们走过"大而空的关卡"的弯路，
> 最终回到**手工设计每个房间 + 强烈的 flow 感**。算法判断不了"什么算好结果"。

结论：**房间是战斗场。** 平台的职责是"改变交战的平面"，不是"提高通过门槛"。

### 8.2 这一版的形状（40 × 15 = 1.5 屏）

```
高台 y=336   c14-c23（10 格）                  可选去处，vista
中台 y=480   c4-c12 / c31-c38（9 / 8 格）      战斗层，清场必经
台地 y=576   c14-c27（14 格）                  中央抬升一格
地面 y=624   c1-c13 / c28-c38（13 / 11 格）    主战场
```

三件事同时变了：

1. **变宽**：26 → 40 列。一屏装不下的房间才像"地方"；进门看不到出口。
2. **变少**：11 块台 → 3 块，每块 8~10 格。少而长，才读得出"一层"。
3. **地面不再是直线**：中间抬一格（624 → 576），切成 13 / 14 / 11 三段。
   平直地面是"程序生成"最强的信号。

### 8.3 出口为什么顺路

右门在地面层，走到台地挡一次，跳一下就过 —— **全程 1 次跳**。

Dead Cells 用**锁门**把人留在房里，不用空间逼人绕路。
门锁着 → 必须清场 → 清场要上中台 → 玩家自己会跳。
**空间不逼你走，敌人逼你上去。** 这是这一版和上一版最根本的区别。

### 8.4 新判据（全部反向，蓝图头声明）

| 键 | 值 | 方向 | 抓什么 |
|---|---|---|---|
| `max_layers` | 3 | 上限 | 层多了把战场切成竖井 |
| `max_platforms` | 5 | 上限 | 平台多而碎 = 浮岛 |
| `min_platform_span` | 6 | 下限 | 2~3 格小岛读不出路径 |
| `min_ground_span` | 10 | 下限 | 近战展不开，只能贴墙打 |
| `max_jump_to_exit` | 1 | **上限** | 出口靠跑酷而不是靠战斗 |
| `min_enemy_layers` | 2 | 下限 | 战斗退化成同层对劈 |
| `min_flying_enemies` | 1 | 下限 | 玩家一直待在地面平面 |

层数按 **96px 分桶**，不按像素精确值 —— 地面 1 格起伏（48px）不该算成多一层，
否则"让地面别是直线"会和"层数上限"直接打架。

### 8.5 四条反向验证（全部抓到）

| 故意改坏 | 报错 |
|---|---|
| case1 改回 11 块 3~4 格小浮岛（上一版） | 层 4 > 3、平台 14 > 5、14 块太短 |

### 8.6 行为验证：机器人真的能打

判据只证明"空间长这样"，证明不了"玩起来有东西做"。
`tests/test_room01_combat.gd` 放一个会追、会打、会跳、会下穿的机器人从进门打到清场：

| 轮次 | 敌人 | 结果 |
|---|---|---|
| 3 只（只靠 320px 察觉半径） | 12.1s 清场 | 挨打 **1** 次、跳很少 —— 那是收割 |
| 7 只 + 全体 `alert()` | 19~21s 清场 | 跳 **34~44** 次、挨打 **4~6** 次 |

房间 1920px 宽，只靠察觉半径会被切成 6 段，玩家进来就是"一间一间地割"。

### 8.7 这一轮踩的四个坑

**下穿必须「↓ + 跳」同按**，光按 ↓ 不触发。机器人的垂直决策因此要成对按键。

## 9. 第四次重做：机关门（2026-11-27 深夜）—— **当前版本**

> ⚠️ **§8 已被本节覆盖。** §8 那版（1.5 屏战斗场、3 层、平地面、出口 1 跳）
> 同样被否，判词：「地形全用几何就行了。问题是你现在设计的房间还是没有可玩性……
> 你这房间太简单了，没有任何迷宫解密的乐趣，完全是个垃圾」。

### 9.1 根因：我第三次把"难度"理解错了

三版的判据分别是：**要求多**（层数 4、必跳 3、岔路 6）→ **要求少**（层≤3、台≤5、
出口≤1 跳）→ 都不对。

真正的错在更上游：**我一直在调几何，而房间从来没有"不让你过"的地方。**
没有拒绝，就没有谜题；没有谜题，再怎么摆平台都只是"走位加长"。

Dead Cells 的答案是现成的 —— **机关门**（`REF_DEADCELLS_ROOM.md §0.5`）：

> 门无法被打破；门上方是一个 3~4 层平台的独立竖井房间；最顶层有开关；
> 扳下开关，门才开。

### 9.2 这一版的形状（34 × 15 = 1632 × 720，1.3 屏）

```
r0        天花板
r1..r12   c22 闸门（12 格满高，顶到天花板，跳不过去）
r3        c17 敌人 / c20 开关            ← 站在 r4 大梁上扳
r4        c5-c8 死路支线 / c14-c21 大梁
r7        c10-c14 第二段台
r10       c7-c11 第一段台 / c25-c31 出口厅掩体
r13       c0..c33 地面（闸门底下也是实心）
```

玩家的动线：

```
进门 → 往右走 → 被闸门挡住 → 抬头 → 斜梯三跳（624→480→336→192）
     → 走到大梁右端扳开关 → 闸门升起 → 从门洞跳下去（落到闸门另一侧）
     → 清掉最后几只怪 → 出口门开 → 走人
```

**上去的路和下来的路不是同一条** —— 这一上一下就是"立体"的来源。

### 9.3 机关门怎么实现的（三处，都不大）

| 文件 | 职责 |
|---|---|
| `world/interactables/SwitchGate.gd` | `StaticBody2D`；`_ready` 里按 `cells` 建碰撞与铁栅；`open()` 幂等，**碰撞当场撤**、栅栏向上抽走 |
| `world/interactables/Lever.gd` | `Area2D`；沿用 `interact_requested` 契约，扳动后 `pulled` 信号 |
| `gen_room_terrain.gd` | 蓝图 `G`/`S` → `Mechanisms/Gate` + `Mechanisms/Lever`（只写位置和格数，几何由脚本自己长） |
| `BaseRoom.gd` | `_bind_mechanisms()`：房间里所有 `pulled` → `Gate.open` |

两个设计取舍：

- **碰撞立刻失效，不等动画。** 玩家扳完开关往往马上就往下跳，等他 0.5 秒会以为没开。
- **几何不打包进 tscn。** 生成器跑的时候场景不在树里（只 instantiate 不 add_child），
  `_ready` 不执行，所以子节点既不会重复也不会被保存 —— tscn 里只留"门在哪、几格高"。

### 9.4 判据（第三次反转：不数几何，证因果）

| 键 | 值 | 抓什么 |
|---|---|---|
| `min_layers` | 4 | 没有纵向空间就没有竖井 |
| `min_platform_span` | 4 | 碎板 |
| `min_ground_span` | 10 | 近战展不开 |
| `min_enemy_layers` | 2 | 同层对劈 |
| `min_flying_enemies` | 1 | 没有空中威胁 |
| **`min_optional_platforms`** | **1** | **每块平台都是必经 = 只有一条路 = 一根梯子** |

外加**机关门三段论**（蓝图里出现 `G`/`S` 就自动验）：

1. 门关着时，开关够得着 —— 否则房间无解。
2. 门关着时，出口到不了 —— 否则门是布景。
3. 门开着时，出口到得了 —— 否则扳了也白搭。

`min_optional_platforms` 的口径要写清楚：在**门关着**的网格上，逐块删掉一段平台，
看还能不能到开关。删了仍然到得了 = 这块"可以不去"。

> ❗ 两个坑：①必须用**原始**网格重建关门副本，传进来的 `grid` 是"门开着"的、
> 里面已经没有 `G`，用它关门等于没关，闸门另一侧的台子会被算成"可选"；
> ②闸门另一侧的台子此刻根本到不了，删不删都不影响开关 —— 必须先排除，
> 否则判据变成摆设。两个坑都真踩过。

### 9.5 行为验证

|---|---|
| 9 只敌人，机器人从进门打到清场 | 12.9s / 跳 16 次 / **挨打 5 次** |

## 10. 收尾时被测试逮到的一个更早的错：相机从来没跟过人

### 10.1 现象

做 Room01 的整间房俯瞰图时，顺手把相机缩放调成"按房间尺寸自适应"，
于是先写了一个 `test_room01_camera.gd` 想确认视角对不对。第一条跑出来是这样：

```
ok   C1 出生点 屏幕 x=120 在 [0,1280]
FAIL C2 闸门右侧 x=1320 屏幕 x=1320 在 [0,1280]
FAIL C3 最右端 x=1600 屏幕 x=1586 在 [0,1280]
FAIL C4 相机中心可用范围 [640,640] 应覆盖 [20,1640]
```

C4 那行 `[640,640]` 是根因：**相机中心永远等于 640**，也就是**相机一动不动**。
屏幕 x 恒等于世界 x —— 玩家走过 x=1280 就从画面右边走了出去，
而房间有 1632 宽。

### 10.2 根因

`BaseRoom.room_bounds` 的默认值是 `Rect2(0, 0, 1280, 720)`，写死在一屏时代。
Godot 的 limit 语义是"**视野边缘**不能越过"，所以 `limit_right = 1280` 让
相机中心最多只能到 `1280 - 640 = 640`。房间一宽，相机就被钉死在原地。

这个错**不会让任何逻辑测试变红**：玩家能走、门能开、敌人会死、场景能切。
它只让一件事不成立 —— **玩家还看得见自己吗**。所以前几轮回归 11/11 全绿，
这间房实际上一直是"人在屏幕外跑"。

### 10.3 修法

不改默认值填 1632（下一间房又要改），改成**留空即自适应**：

- `room_bounds` 默认 `Rect2()`；非零才当手动覆盖。
- `_derive_room_bounds()` 从 `Terrain/Solids` 的碰撞矩形合并出 AABB ——
  用玩家**真正撞得到的那一圈墙**算边界，一定和玩家能去的地方重合。

### 10.4 判据

`tests/test_room01_camera.gd`，四条，全部用**屏幕坐标**断言而不是 `cam.limit_*`：

| 用例 | 断言 |
|---|---|
| C1 出生点 x=120 | 屏幕 x ∈ [0,1280] |
| C2 闸门右侧 x=1320 | 屏幕 x ∈ [0,1280] |
| C3 最右端 x=1600 | 屏幕 x ∈ [0,1280] |
| C4 视野边界 | `limit [16,1648]` 覆盖房间 `[16,1648]` |

反向验证：把 `room_bounds = Rect2(0,0,1280,720)` 注回 `Room01.tscn`，
C2/C3/C4 立刻变红（`屏幕 x=1320` / `x=1586` / `[0,1280]`）—— **1/1 抓到**。

### 10.5 顺带补的两处

| 项 | 之前 | 现在 |
|---|---|---|
| 闸门"锁着"的表现 | 只有铁栅，靠撞墙理解 | 门中央一颗**呼吸红灯**，开门转绿并淡出（`LockLamp`，判据 G5） |
| 核心动线未被证明 | G4 只证了"门开着能从地面走过去" | 新增 G6：从 r4 大梁走进门洞，落到闸门**另一侧** |

G6 实测落点 `(1530, 480)` —— 不是地面而是 r10 那块平台的台面：
一边下坠一边按着右键，横向飘了 240px 正好落上去。
这是房间的真实行为，判据只要求"到对面且下来了"，不规定落在哪块砖上。

### 10.6 回归

12 项：`room01_gate / room01_camera / room01_combat / room01_complete /
room01_traverse / room_terrain / gameplay_loop / death_loop / enemy_ai /
fold_lock / jump_height / env_light` 全绿（另有一项 `rest_and_transition`
是既有失败：安全屋复活点偏 8px，与本轮无关）。

## 11. 第五次重做：从"一间房"变成"一关"

```
c29..c48  主脊      8 行净高，一段地台
c42..c48  竖井      从主脊天花板开到 r8，六级平台 —— **全关唯一的上升路线**
c46..c62  上层走廊  扳开关的地方，c58..c60 是三格宽的下坠井
c49..c63  东厅      下坠落点，也是闸门前最后一块战场
c64       闸门      26..36 共 11 格满高，门上方是一整面墙
c65..c98  出口走廊  支线：小竖井 G 通瞭望台，c92 通高空死路 J
```

动线：进门 → 高厅 → 主脊 → 东厅被闸门拦住 → 回头进竖井，六跳上到上层走廊 →
往右扳开关 → 走下坠井回到东厅 → 穿门 → 出口走廊。**上去和下来不是同一条路。**

### 11.4 新判据：`min_walk_px`

前四版的判据（层数、平台宽度、跳数、可选平台）全部只能量"结构对不对"，**量不出"够不够大"** ——
上一版全部绿灯，可它就是 1.3 屏。

所以这一版加了一条直接量那个数的判据：**从出生点到右门的最短路径（像素）**。
Dijkstra 跑在站面图上，边权 = (横向格差 + 纵向格差) × 48 —— 不是纯水平距离，
竖井里那六跳也要算进去，否则"往上爬"不产生距离。

```
✓ 到出口最短路径 5232px（4.1 屏宽）≥ 3600px
```

门槛 3600（2.8 屏宽）：低于这个数就是"一路小跑就到底"，直接拒绝生成。

## 12. 线框稿模式：先把美术全拿掉

### 12.1 触发

白哥原话：

> 「你把所有贴图都去掉，出单纯的线框设计稿，然后在这个线框设计稿玩，
> 被认可了以后完了以后把线框替换成贴图。不然现在贴图素材不全，
> 看起来乱七八糟，反而更麻烦」

这句话点的是一个顺序问题：**我一直在"半成品美术"上改设计**。
地表贴图只铺了地面、背景只有一盏径向光、墙是一整块棕色矩形 ——
每次截图出来，我分不清"这地方不好玩"和"这地方不好看"，白哥看到的也是同一个东西。

所以改成两段式：**先证明空间成立，再往里面填美术**。

### 12.2 开关

蓝图头部一行：

```
wireframe=1
```

- `1` → 线框稿（Terrain 里一个贴图节点都不许有，生成器自检）
- `0` 或删掉 → 原来的贴图版
- **只要重跑生成器，地形一格不动**。蓝图是唯一真相，模式不是房间属性。

### 12.3 线框版长什么样

| 元素 | 贴图版 | 线框版 |
|---|---|---|
| 背景 | 每屏一盏径向光（1280×720 平铺）+ 顶部压暗 | 一块纯深色 `WireBackdrop`，没有渐变 |
| 实心地形 | 整块棕色 `ColorRect` | 淡填充（`#2E3641`）+ `Line2D` 亮描边（`#808F9F`） |
| 单向平台 | 投影 + 描边 + 台面 + 顶面 + 底边，五层 | 一条橙色横线 + 两端短竖脚 |
| 地表贴图 | `Sprite2D` × 每 2 格一块 | **没有** |
| 天花板岩笋 | 6 个 `Polygon2D` | **没有**（它不参与玩法） |
| 玩家 | 像素动画 | 青色矩形框 + 朝向短线（34×64，等于碰撞盒） |
| 地面敌人 | 史莱姆/尖刺球贴图 | 红色菱形 |
| 飞行敌人 | 蝙蝠贴图 | 黄色三角 |
| 机关拉杆 | 棕底座 + 橙柱头 + 斜臂 | 米白：两条竖脚 + 斜杆 + 圆头（`WireOverlay` 重画） |
| 摆件 | 图标 | 灰色小方块（位置不变，只换画法） |
| 后处理 | 紫月环境光 / 去饱和 / 纸纹 | 整个 `PostProcessLayer` 隐藏 |

三类颜色各有分工，互不重叠：**橙色 = 能站的，红色 = 会咬人的，黄色 = 会飞的，
青色 = 你自己，米白 = 能扳的**。看错任何一种都会直接影响判断，所以不共用颜色。

### 12.4 判据（`tests/test_wire_mode.gd`）

| 用例 | 断言 |
|---|---|
| W1 | `Terrain` 子树里 0 个 `Sprite2D` / `TextureRect` / `Polygon2D` |
| W2 | 房间根下有 `WireOverlay`，且挂了脚本 |
| W3 | `Player/Visuals/Sprite` 已隐藏 |
| W4 | 场上 ≥10 只敌人，且**每一只**的 `Visual` 都隐藏 |
| W5 | `Terrain/Blocks` 里描边是 `Line2D`，实心色块 0 个 |
| W6 | `PostProcessLayer` 已隐藏 |

**反向验证**：把键改成 `wireframe=0` 重新生成 → W1/W2/W3/W4/W5 **全部变红**：

```
FAIL W1 Terrain 里 0 个贴图节点（实际 101）
FAIL W2 房间根下有 WireOverlay（实体占位）
FAIL W3 玩家的 pixel sprite 已隐藏
FAIL W4 全部敌人的 Visual 都已隐藏（漏了 23 只）
FAIL W5 地形轮廓用 Line2D 画（描边 0 条，实心色块 22 个）
```

W6 单独反向验证：把 `visible = false` 改回 `true` → W6 立刻红。

### 12.5 这一轮踩的四个坑

| 坑 | 现象 | 根因 |
|---|---|---|
| 反向验证"假绿" | 改成 0 之后测试还是全绿 | 蓝图注释里写了 `wireframe=1`，批量替换命中了**注释行**，键没动。注释里不许再出现 `key=值` |
| 墙和空分不开 | 俯瞰图读不出哪里是实体 | 填充 `0.118` vs 背景 `0.072`，只差 12/255。提到 `0.18/0.21/0.25` |
| 血条漏进截图 | 明关掉了 HUD，拍了 40 帧又回来了 | `TouchHUD._process` 每帧按血量自己设 `visible`。要同时 `process_mode = DISABLED`，而且**等帧之后要再压一次** |
| 拉杆底座看不见 | 只看到一个悬空的圆头 | 底座横线画在 `y=0`，和地板顶面的描边完全重合。改成两条竖脚 + 换成米白 |

另外两条不是坑，但值得记：

- **实体占位用 `_draw` 而不是给每个实体挂节点**：敌人是运行时生成的，
  挂子节点的时机对不上；`_draw` 每帧按当前位置画，天然跟着动画、击退、死亡走。
- **`WireOverlay` 节点存在 = 线框模式**：不在场景里存一个 `wireframe=false` 的属性。
  切回贴图时这个节点根本不生成，房间脚本、玩家脚本、敌人脚本都不知道它存在过。
