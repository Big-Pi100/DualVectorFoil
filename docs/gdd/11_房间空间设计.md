# 11 · 房间空间设计

> 建 2026-11-27。触发：白哥原话「**真正不可玩的东西就是一个房间根本没有任何设计。
> 先从房间的空间设计做起，你现在的一间房间根本算不上一间房间，就只有一条路，
> 恶魔城最大的特点地图和地形你根本就没设计**」。
>
> 这份文档回答的是**一间房的地形怎么长出来**，不是摆件、不是背景（那是 `09` 和美术）。
> 落地产物：`godot/world/rooms/blueprints/*.txt` + `godot/world/tools/gen_room_terrain.gd`。

## ⚠️ 2026-11-27 第五次修正：房间必须**拒绝**玩家（最新，覆盖下面全部）

> 下面这一节（第四次修正）**只对了一半**。它把房间压成"层数少、平台少、平地面、
> 出口 1 跳"，结果被白哥一句话否掉：
> 「地形全用几何就行了。问题是你现在设计的房间还是没有可玩性……
> 你这房间太简单了，没有任何迷宫解密的乐趣，完全是个垃圾」
>
> 错在把"战斗为主"读成了"空间要简单"。Dead Cells 每个房间都有**一个不让你过的地方** ——
> 被囚者的牢房必有的「机关门」：门打不开，门上方是 3~4 层平台的独立竖井，
> 最顶层有开关，扳下才开门。
>
> **真正的规则：房间 = 一个必须解决的问题 + 解决它的空间 + 解决过程中的战斗。**
> 完整拆解见 `docs/ref/REF_DEADCELLS_ROOM.md §0.5`，落地实现见
> `docs/gdd/12_单房完整实现.md §9`。
>
> 判据也从"数几何"改成"证因果"：
> 门关着时开关够得着 / 门关着时出口到不了 / 门开着时出口到得了 / 至少 1 块平台可以不去。

## ⚠️ 2026-11-27 第四次修正：判据整体反转

**这一节覆盖下面所有"层数越多越好 / 必跳次数越多越好"的说法。**
（但上面第五次修正又推翻了本节里"越少越好"的部分 —— 两节都要读。）

白哥连着否掉两版房间（三级台阶、错位网格 11 块板）之后说了那句
「**你好好研究一下重生细胞的房间是怎么设计的**」。研究结论写在
`docs/ref/REF_DEADCELLS_ROOM.md`，最核心的一条：

> GDC 2019，Motion Twin 的 Sebastien Bénard：
> *"Platforming is just a means to move, to avoid enemies, to position yourself,
> it's not a hardcore platformer game."*

**房间是战斗场，不是跑酷题。** 所以：

| 维度 | 旧判据（错） | 新判据（对） | 为什么 |
|---|---|---|---|
| 层数 | `min_layers ≥ 3` 越多越好 | **`max_layers ≤ 3`** | 层多了战场被切成竖井 |
| 必跳 | `min_jump_to_exit ≥ 3` | **`max_jump_to_exit ≤ 1`** | 难度该来自战斗，不来自跑酷 |
| 平台 | 11 块、3~4 格小浮岛 | **`max_platforms ≤ 5`、每块 ≥ 6 格** | 小岛读不出路径，只是浮板 |
| 岔路 | `min_alternate_stands ≥ 6` | 删除该判据 | 支线不是目的；Dead Cells 靠**锁门**留人 |
| 地面 | 没量 | **`min_ground_span ≥ 10`** | 近战要展开，不能贴墙打 |
| 敌人 | 没量 | **`min_enemy_layers ≥ 2` + `min_flying_enemies ≥ 1`** | 否则退化成同层对劈 |

一句话概括这次错误的性质：**判据越"严格"，房间越像跑酷游戏。**
旧判据全部 PASS 的那一版，正是白哥说"依然还是垃圾"的那一版。

另外两个结构结论：

- **一屏装不下的房间才像"地方"。** 前两版都是 26×15 = 1248×720 = 正好一屏，
  一眼看穿 —— 这才是"盒子感"的根因，不是"平台不够多"。Room01 已改 **40×15（1.5 屏）**。
- **完全平直的地面是"程序生成"最强的信号。** Dead Cells 的地面从来不是一条直线。
  Room01 的中央台地（抬一格）就是为这个加的，同时给近战一个高地。

## 0. 先把事实钉住：六间房原本是一个矩形

逐文件读 `world/rooms/Room0*.tscn`，六间房的碰撞体是同一个东西：

```
[node name="Floor" type="StaticBody2D"]
position = Vector2(640, 620)
[CollisionShape2D] shape = RectangleShape2D(1200, 40)
```

- **每间房只有 1 个碰撞矩形**，1200×40，顶在 y=600
- **两扇门都在 y=540**（同一高度）
- **零平台、零台阶、零竖井、零柱子**

所以"只有一条路"不是感觉，是几何事实：从左门到右门是一条 1200px 的水平直线，
中间没有任何需要跳、需要绕、需要回头的地方。

在它上面加敌人、加 AI、加技能都没有用 —— **地形不提供任何问题，能力就没有用武之地**。
这是把它排在 S0（敌人 AI）之前的原因。

## 1. 层高预算：先有尺子，再画图

所有平台间距都取决于一个数：**玩家单跳能跳多高**。

### 1.1 实测（不是推算）

原代码 `jump_velocity = -490`、`gravity_scale = 1.35`，反算单跳只有 **91px（1.9 格）**。
而 `FEEL_TABLE.md`、`02`、`04`、`06`、`07` 全部写 **203–204px（4.25 格）**。
**代码和文档差 2.2 倍** —— 玩家实际只能跳 1.9 格，任何平台设计都不可能成立。

按 `FEEL_TABLE` 的两个数（高度 204、滞空 917ms）联立解出：

| 量 | 解 | 现在代码 |
|---|---|---|
| 重力 | `g = 2h/(T/2)² ≈ 1941` | `980 × 1.98` = 1941 ✅ |
| 起跳初速 | `v = g·T/2 ≈ 890` | `-890` ✅ |
| 二段增量 125px | `v = √(2·1941·125) ≈ 697` | `-697` ✅ |

`tests/test_jump_height.gd` 用真实物理帧实测：

| 量 | 实测 | 判定区间（FEEL_TABLE ±5%） |
|---|---|---|
| **单跳高度** | **211.6px（4.41 格）** | 196–212 |
| **滞空** | **950ms** | 880–970 |
| **二段总高** | **331.1px（6.90 格）** | —（CANON 写 331） |
| 二段增量 | 119.5px | 116–142 |

### 1.2 由此得出的设计预算（照着用，别再算）

| 用途 | 落差 | 说明 |
|---|---|---|
| 台阶（走着就能过） | **≤ 1 格（48px）** | 直接跨上去，不用跳 |
| **主路平台（推荐）** | **3 格（144px）** | 单跳 4.41 格，余量 1.4 格，不挑手感 |
| 主路上限 | 4 格（192px） | 只剩 0.4 格余量，**别当常态用** |
| **折叠专属** | **5–6 格（240–288px）** | 单跳上不去、二段（6.9 格）上得去 |
| 装饰性高差（跳不上） | ≥ 7 格（336px） | 柱子、垂饰、纯视觉分割 |

> ❗ 上表的"格"= `TILE = 48`。改跳跃参数必须重跑 `test_jump_height.gd`，
> 否则这张表全部失效，而房间看起来仍然是"对的"（这是最坏的一种错）。

## 2. 网格：高度 15 行固定，宽度按房声明

| 项 | 值 | 理由 |
|---|---|---|
| `TILE` | 48px | 与全部资产同一把尺子（`04 §10`） |
| 视口 | 1280×720 | `project.godot` |
| 房间高度 | **15 行（720px）** | 与视口同高，纵向不出屏 |
| 房间宽度 | **按房定** | Room01 = 34 列（1.3 屏，镜头横向滚动）；其余 = 26 列（1 屏） |
| 网格原点 | `(16, 0)` | 1248 居中于 1280，左右各留 16px |
| 玩家高 | 46px | 不到 1 格，站在格内 |

> **为什么 Room01 不再是 26 格。** 26×15 生成出来正好一屏，玩家进门一眼看到出口，
> 房间退化成"背景板"而不是"地方"。40 列之后镜头必须横向滚动，
> 进门看不到出口，空间才开始有"里外"。
> （最终定在 34 列：40 列时闸门右侧有 16 格空走廊，纯浪费；收到 34 之后
> 闸门右侧只剩 10 格，出口厅才有"尽头"的感觉。）
>
> 宽度变化的代价只有一处：`_build_backdrop` 原来写死 1280×720，房间变宽后右侧
> 漏出 viewport 的深灰 —— 已改成按 `cols * TILE` 算。**这是"尺寸写死"惯性的又一次复发。**
>
> 之前的地板 1200×40：宽 1200 不是 48 的倍数（1248 才是），厚 40 不是 48 的倍数，
> 顶 y=600 也不在格线上（624 才是）。**三个维度全都对不齐网格**，
> 所以贴图只能用 `offset (-640,-20)` 硬凑 —— 这是"看着有点怪但不说不出哪怪"的来源。

## 3. 蓝图：地形是数据，不是场景里手摆的节点

### 3.1 格式

`godot/world/rooms/blueprints/<id>.txt`：

```
! 注释（! 开头，不进网格）
room_id=room_02
scene=res://world/rooms/Room02.tscn
door_L=res://world/rooms/Room01.tscn|SpawnFromRight|← 画页一
door_R=res://world/rooms/Room03.tscn|SpawnFromLeft|→ 画页三
---
##########################   ← 15 行，每行 26 字符
#........................#
...
```

字符集：

| 字符 | 含义 |
|---|---|
| `#` | 实心地形（灰盒 + 碰撞，层 1） |
| `=` | 单向平台（可从下方跳穿、按下+跳下穿，层 2） |
| `.` | 空 |
| `L` / `R` | 左门 / 右门（必须分别在第 0 / 最后一列） |
| `P` | 出生点（可选，不给就由门推断） |
| `E` | 敌人生成点（落在该列最低地面，蓝图几个 `E` 就是几只） |
| `A` | 能力拾取点（能力 id 由头部 `ability=<id>` 给出） |

门洞是 **3 格高**：门标记只在中心那格，上下各留一格空 ——
否则"门口头顶是墙"会让玩家进不去（第一版就栽在这，验算器报"全房不可达"）。

**`A` 的位置有硬约束**（S2 用四次实拍换来的）：

| 不能放 | 为什么 |
|---|---|
| 高台/悬空体正下方 | 台底 528、玩家头顶 570，起跳只升 **50px** 就撞头 —— 捡到能力当场试跳试不出来 |
| 已有 UI 标签的附近 | `VistaPoint` 的「驻足·眺望风车」标签和拾取提示会叠成两行字 |
| 屏幕右下 1/3 | 触屏按钮（技1/技2/滚/盾/跳/攻）会把提示整个盖住 |

判据：`gen_room_terrain` 会拒绝「`A` 脚下没有地面」，但**拒绝不了"能捡到却看不清"** ——
那条只能靠实拍（`tools/shot_ability.gd`）。

头部可选键：

| 键 | 作用 |
|---|---|
| `ability=<id>` | 有 `A` 时必填，`fold` = 折叠（二段跳） |
| `vista_at=<列>,<行>` | 把 `VistaPoint` 摆到该格站面上方 40px。**不写就保持原位不动**（因为观景点不一定贴地） |

### 3.2 为什么用文本而不是手摆 tscn

| 手摆 tscn | ASCII 蓝图 |
|---|---|
| 摆完不知道跳不跳得上去，要人肉试 | 生成前**自动验算可达性**，跳不到直接拒绝生成 |
| 改一处要动十几个节点，容易漏 | 改一个字符 |
| diff 是一堆坐标，review 看不出形状 | diff 就是形状 |
| 无法断言"这间房有层次" | 测试直接数站面高度 |

生成器：`godot/world/tools/gen_room_terrain.gd`

```bash
"E:/godot/Godot_v4.7.2-stable_win64_console.exe" --headless --path godot \
  --script res://world/tools/gen_room_terrain.gd -- room_02
```

产物节点：

```
Room02
├─ Terrain (z_index=-10)
│   ├─ Backdrop        纸色全屏底（没有它就是深灰虚空，房间像几块板浮着）
│   ├─ Solids          StaticBody2D 层1 + N 个合并后的矩形
│   ├─ Blocks          ColorRect 灰盒（**待美术**）
│   ├─ Platforms       StaticBody2D 层2 + one_way_collision
│   ├─ PlatformVisuals
│   └─ GroundArt       Sprite2D 逐块地表贴图（ground_mid 的 4 帧循环）
├─ Doors/  DoorToXxx（Area2D + 碰撞 + Label）
├─ SpawnFromLeft / SpawnFromRight / SpawnFromRest
└─ Player / TouchHUD / PostProcessLayer / InvadersContainer / VistaPoint（保留不动）
```

> **为什么不挂 TileMapLayer**：TileMapLayer 的一个 cell 等于 `TileSet.tile_size`，
> 而 `ground_mid` 被切成 96×144（2 格宽 × 3 格高）。我们的网格是 48，
> 于是 cell `(c,r)` 落在 `96c × 144r` 上 —— 跟 48 网格、跟任意地表高度（624/672/528）全部对不齐。
> 第一版就是这么写的，瓦片被铺到 **y=1872 的屏幕外**，代码没报任何错，只有实拍截图才看出来。
> Sprite2D 的位置是自由像素坐标，能精确压在任意一行地表上。

### 3.3 生成器会拒绝什么

| 拒绝条件 | 为什么 |
|---|---|
| 每行宽度不一致 | 网格必须矩形 |
| 出现非法字符 | 拼错一个字符会静默变成空地 |
| `L` 不在第 0 列 / `R` 不在最后一列 | 玩家会卡在房间里 |
| **有门从出生点不可达** | **这间房会把玩家永久卡死** |
| `A` 脚下没有地面 | 纸片悬空，玩家够不到 |
| 有 `A` 但头部缺 `ability=` | 不知道要解锁哪个能力 |
| 蓝图头缺 `scene=` / 门缺 `door_X=` | 生成出来的房间进不去 |

**只能靠人做、生成器做不了的一步**：上锁之前逐间量「单跳还通不通」。

```bash
for r in safe_house room_01 room_02 room_03 room_04 room_05; do
  godot --headless --path godot --script res://world/tools/gen_room_terrain.gd -- "$r" --audit
done
```

`--audit` 只验算不写文件，复用同一份 `_reachability`（**不另写审计脚本** ——
那就是第二份判据，两边迟早对不上）。2026-11-27 的实测结论：

| 房 | 孤岛 | 判定 |
|---|---|---|
| SafeHouse / Room01 / Room02 / Room05 | 0 | 全通 |
| Room03 | 6（高台 c12-17 r7） | **故意的**，这就是折叠点 |
| Room04 | 8（柱顶 4 + 中间台 4） | 柱顶 480px 二段也上不去 = 纯装饰；中间台 240px 属"折叠后奖励位" |

**门全部单跳可达** —— 所以上锁不会卡死任何人。这一步是 S2 最容易漏的。

## 4. 六间房各自的空间性格

**不要六间长得一样。** 每间房回答一个问题，形状就是答案。

| 房间 | 切片角色 | 空间性格 | 关键尺寸 |
|---|---|---|---|
| `Room01` | [A] 入口 | **机关房**：地面被满高闸门切断，唯一出路是爬三段斜梯到大梁、扳开关、从门洞跳下去；左上有一条只放观景的死路 | 34×15（1.3 屏）/ 4 层 / 5 块台 / 9 只敌人 / 闸门 12 格满高 / 细节见 `12 §9` |
| `Room02` | [B] 高台房 | **分层**：四级站面、两条路都能通顶、右侧台地把门抬高 | 台地顶 528，右门 y=552（左门 600） |
| `Room03` | [D] 死巷 | **折叠专属**：一块悬空高台，单跳够不到、二段够得到 | 台地顶 384，落差 240px（5 格） |
| `Room04` | 前厅 | **对称**：两根垂柱分三跨，中央抬高 | 柱底 480（不落地，人从下面过） |
| `Room05` | Boss | **留白**：中间 12 格平地，两侧 2 格看台 | 看台顶 432 |
| `SafeHouse` | [C] 休息 | **小**：天花板压到 r5，可用高度只剩 8 格 | 全房最矮 |

### 4.1 Room02 的两条路（"不是一条路"的具体形态）

```
地面(y=624) ─┬─ 左链 → r9(c3-6, 432) → r6(c7-12, 288) → r3(c11-15, 144)
             └─ 右链 → r9(c15-18, 432) → r6(c18-23, 288) → r3 ─┘
```

两条链在顶层汇合。走地面的人要跨过 c7-c10 的 1 格深坑；
出门在右侧台地上（y=528），**必须先跳上 2 格台**才能碰到门。

### 4.2 Room03 为什么台地要悬空

台地顶 384、底 528。玩家站地面时头顶在 578 —— **从台地下面走得过去**。

如果台地落地（顶 384 一路实心到底），它就是一堵 5 格高的墙，
而折叠正是在这间房才拿到的 —— **玩家会被自己的目标挡在门外**。
这是设计事故，不是难度。生成器的可达性验算第一次就把这个抓出来了。

**悬空带来的第二个后果（S2 发现的）**：台底只有 2 格净空，
在台正下方起跳会**撞头 50px 就掉回来**。所以能力纸片不能放在台底下 ——
玩家捡到折叠当场试跳，只会一头撞在台底，然后以为"这东西没生效"。
纸片放在台左侧 c9（头顶全空），捡完右移一步就是台边。

**台面同时是观景点的位置**（`vista_at=13,7`）。这是切片里唯一一处
「能力 → 地图回报」的闭环：折叠解锁前连台上的标签都够不着，
解锁后站上去才拉远相机看到风车。台子不能是空的 —— 空的台只是"能上去"，
不是"值得上去"。

## 5. 判据（已进 CI）

`tests/test_room_terrain.gd`：

| 判据 | 阈值 | 抓什么 |
|---|---|---|
| 结构齐备 | Solids / Platforms / GroundArt / Backdrop / Doors 都在 | 生成器被改坏 |
| **站立面高度数** | **≥ 3 个不同高度** | 退回"一层平地" |
| 玩家落点 | 90 帧内 `is_on_floor()` 且 y < 760 | 穿地、掉出房间 |
| **单向平台可跳穿** | 从下方起跳后脚 ≤ 台面 +10px | `collision_layer` 写错 / `one_way_collision` 没开 |

最后一条最值钱：平台碰撞层配错时，玩家被平台从下方顶头，
**场景、贴图、编辑器预览全部正常**，只有真跳一次才发现。

生成器另有可达性验算（BFS，单跳 204px / 水平 4 格），门不可达直接 `exit 1`。

### 5.1 结构可玩性判据（2026-11-27 反转，`12 §7`）

「门能到」不等于「房间好玩」。三级台阶也能让门必须跳着才到，但它仍然是一条走廊。

> ❗ **这一组判据换过方向。** 初版要求「层数多、必跳多、岔路多」，
> 结果把房间逼成了跑酷塔 —— 判据全绿，房间更难看，被连着否了两版。
> 现在的版本要求「**层数少、平台少而长、地面开阔、出口顺路**」。
> 反转的完整依据见本文开头的「第四次修正」与 `docs/ref/REF_DEADCELLS_ROOM.md`。

| 键 | 方向 | 抓什么 |
|---|---|---|
| `max_layers` | 上限 | 层多了把战场切成竖井 |
| `max_platforms` | 上限 | 平台多而碎 = 浮岛 |
| `min_platform_span` | 下限 | 2~3 格的小岛读不出路径 |
| `min_ground_span` | 下限 | 近战展不开，玩家只能贴墙打 |

| `min_enemy_layers` | 下限 | 战斗退化成"同一层对劈" |
| `min_flying_enemies` | 下限 | 没有空中威胁，玩家一直待在地面平面 |

## 第六次修正：**尺度本身是设计**

第五次修正（机关门）解决的是"房间会不会拒绝你"。第六次解决的是另一件事：**它有多大**。

白哥的原话：

> 「这是细胞重生的单房间地图，能玩2-5分钟。你设计那个地图10秒都玩不了」

配的是一张《死亡细胞》的关卡地图截图 —— 一整关：一条长主脊、挂在两边的六七个房间、
两处竖井、三个不同方向的出口。**"单房间"指的是"一关"，不是"一屏"。**

### 结论：一关的最小尺寸

| 指标 | 下限 | Room01 实测 |
|---|---|---|
| 到出口最短路径 | ≥ 2.8 屏宽（3600px） | 5232px（4.1 屏宽） |
| 网格 | ≥ 90 × 36 | 100 × 40 |
| 高度层 | ≥ 6 | 9 |
| 敌人 | 密度跟着面积走，4800px 至少 20 只 | 23 |
| 纯跑图时间（机器人最优路线） | ≥ 30 秒 | 33.1 秒 |

### 为什么之前所有判据都没拦住

层数、平台宽度、跳数、可选平台数 —— 这些量的是**结构**，不是**体量**。
一间隔 10 秒能跑完的房，照样可以有 4 层、5 块台、1 条死路，判据全绿。

所以新增 `min_walk_px`：直接量"从出生点到出口最短要走多少像素"。
它是唯一一条**不可能被小房间满足**的判据 —— 结构可以糊弄，距离糊弄不了。
