# 13 · 关卡拼装：把「混合方法」落成代码

> 起因：白哥给了《死亡细胞》的生成方法论（Motion Twin / Sébastien Bénard 的分享），
> 核心是**设计师手工造零件，算法按蓝图拼装**。
> 原文一句话概括：*纯随机会造出迷宫，但判断不了什么好玩；所以用手工房间保质量下限，
> 用关卡图和拼装保变化。*

这一章记的是：**那六个步骤，本项目的代码做到哪一步了**，以及做完之后撞到了什么。

---

## 13.1 六步对照：我们只做了半步

先说实话。对着代码一条条数：

| DC 的步骤 | 本项目 | 证据（代码里的现状） |
|---|---|---|
| **1 铺设画框**（主题、固定节点） | ❌ 没有 | 蓝图头部没有 `theme=` 之类的键；`wireframe=1` 只是临时美术开关 |
| **2 准备积木**（房间模板） | 🟠 **有 6 间，但没有契约** | `rooms/blueprints/*.txt` 是手写 ASCII；门槽位是隐式的（靠 `L`/`R` 字符所在行推算），没有 tag、没有同功能变体、没有尺寸声明 |
| **3 绘制蓝图**（关卡图） | ❌ 没有 | 顺序写死在 `door_R=res://world/rooms/Room03.tscn` 里，是一条硬链，不是图 |
| **4 生成脊柱**（关键路径） | ❌ 没有 | 房间内部有 `min_walk_px`，那是「房间内动线」，不是关卡关键路径 |
| **5 填充血肉**（拼接） | ❌ 没有 | 靠 tscn 的 `DoorTo*` 手工连 |
| **6 注入灵魂**（内部随机化） | ❌ 没有 | 敌人位置写死在蓝图的 `E` 里，`_build_enemy_spawns` 只负责把字符变成 Marker2D |
| 种子系统 | ❌ 没有 | `grep seed` 只命中作物播种，没有游戏种子 |

**所以真正的缺口不是「房间设计得不好」，是「根本没有生成系统」。**
之前六次改 Room01，改的都是"零件"，而零件再好也只产出同一关。
这也是为什么改到第六版，白哥仍然觉得"还是那条走廊"——**因为变化这一维根本不存在**。

## 13.2 补上的四步

新增两个文件，一共约 500 行：

```
world/level/
  level_01.graph      ← 第 3 步：关卡图（人写，一份 12 行）
  gen_level.py        ← 第 4/5/6 步：布局、拼接、重洒敌人（约 450 行）
  level_01.layout.json ← 产物：每间房的 origin / 模板 / 门行 / 敌人数
  Level01.tscn        ← 产物：拼好的整关场景
```

### 关卡图长这样

```
seed=20261127

node entry    tag=start    template=room_02
node combat_a tag=combat   template=room_03,room_04,room_02   after=entry
node combat_b tag=combat   template=room_04,room_03,room_02   after=combat_a
node atrium   tag=combat   template=room_01                   after=combat_b
node shop     tag=shop     template=room_04                   after=atrium
...
```

- `tag` = 这间房在关卡里的**职能**，同时决定敌人密度（`TAG_SPAWNS`）；
- `template` = 该职能的**候选池**，拼装时按种子抽一个 —— 这就是"变化"；
- `after` = 父节点。

### 拼装的两条硬规则

**① 用「站面行」对齐，不用「门格行」。**

Room02 的 `R` 门格在 r11，但 r12 是空的、r13 才是地，玩家站的是 r12。
拿门格行去对齐，接缝处会差 48px，人卡在门框上。
所以 `stand_row()` 要往下找到第一块实地，取它上面那一行。

**② 不重叠，并排 + 事后挖门洞。**

第一版用了「重叠一列」（`child.col = parent.col + cols - 1`），
结果接缝是一道竖墙，中间只剩 **1 格宽（48px）** 的缝：玩家碰撞盒 34px，
能挤过去但一直蹭墙，画面上也不像"两间房连通"，像"两堵墙夹一条缝"。

改成并排（`+ cols`）之后，再把两侧各一列、门洞高度 3 行挖空 ——
**2 列宽（96px）× 3 格高（144px）** 的门洞。这个洞不属于任何模板，
是拼装产生的，所以由拼装器负责开（`punch_seams`）。

### 敌人重洒

模板里的 `E` / `F` / `A` 在合并时**全部丢弃**，按 tag 重新放：

| tag | 地面 | 飞行 | 为什么是这个数 |
|---|---|---|---|
| start | 2 | 0 | 进门先教打架，别一上来就围殴 |
| combat | 5 | 1 | 一屏 5 个，正好一场遭遇战 |
| shop | 0 | 0 | 商店房必须能安全翻背包 |
| treasure | 1 | 1 | 有守卫，但不至于挡住宝箱 |
| boss | 3 | 1 | 前厅留白比堆怪重要 |

同一列至少隔 3 格（144px），否则敌人叠在一起，玩家分不清在打谁。

## 13.5 撞到的三件事（不粉饰）

### ① 拼装救不了零件

`room_02/03/04/05` 都长这样：一个 26×15 的盒子，里面 3 条横线，敌人排在地面一条线上。
拼 7 间出来，就是「7 个空盒子排一排」。**引擎是对的，输入是空的。**

DC 的房间模板一屏里有 3~4 层、上下贯通、还有竖井和转角；
我们的模板是"盒子里放几条平台"。这一层不补，再好的拼装也只能产出空房间。

### ② 种子只换了皮，没换骨

跑了四个种子，结果：

| seed | combat_a | combat_b | combat_c | 尺寸 | 敌人 |
|---|---|---|---|---|---|
| 20261127 | room_03 | room_04 | room_02 | 182×15 | 26 |
| 7 | room_04 | room_03 | room_03 | 182×15 | 26 |
| 42 | room_04 | room_03 | room_02 | 182×15 | 26 |
| 2026 | room_04 | room_04 | room_03 | 182×15 | 26 |

模板组合变了，但**尺寸恒定、房间数恒定、敌人总数恒定**。
玩家看到的变化只有"这个位置换了个房间"。

真正该随种子变的维度是：房间数（8~12）、房间尺寸（一屏 / 两屏 / 高塔）、
分支结构（有没有支线、死路、宝箱房）、垂直层次。
这四个维度现在都是常数。

### ③ 抬头看不见东西

站在 room_01 的入口高厅地面上，视野 720px，而厅高 19 行 = 912px ——
**抬头只能看到一片空**。第一张特写拍出来几乎是全黑的，只有脚下一条线。

不是相机问题，是**净高超过一屏却没有足够的平台填充**。
DC 的纵深靠"每一屏都有东西"来支撑；我们的大房间只有 4 段平台。

## 13.6 下一步

按 DC 的工作顺序（先零件，后拼装），下一步应该是**补零件**，不是继续改引擎：

1. **模板加「上下门」（`U` / `D`）**：现在只有左右门，关卡图只能一维排开。
   加了上下门，才能做 2D 网格布局（横向主干 + 纵向支线），这是 DC 的基本形态。
2. **造 3 类新模板**：
   - 多层厅（26×30，3~4 层平台 + 竖井，站地面能看见上层）
   - 高塔（26×45，向上爬，出口在顶部）
   - 转角房（左进上出 / 上进右出，用来把横向主干折起来）
3. **关卡图升级成 2D**：节点带 `(x, y)` 网格坐标，主干走横向，支线纵向挂着。
4. 零件够了之后，再回头跑种子对比 —— 那时候"不同种子"才真的像另一局。

在这一步完成之前，**Room01 的"游戏水平"问题没有解决**：
它现在只是「8 间房里的 1 间」，而且是最空的那类之一。

# 14 · 垂直拼接：让关卡第一次不是一条线

> 2026-11-27 第七次。上一节列的 4 条待办，这一轮做掉了前三条。
> 结果是本项目第一张**真正 2D 的关卡图** —— 有上升、有竖井、有落差。

## 14.1 为什么「加两个门字符」是结构性改动

在补 U/D 之前，关卡图的表达能力被硬件限死了：

```
node A after=entry
node B after=A
node C after=B
```

`after` 只能是"父的右门 → 子的左门"。于是无论模板池里放多少新房间，
**产出的拓扑永远是 `A→B→C→D` 一条链**。换种子只换零件的长相，不换路。

这是上一轮「四个种子尺寸全一样」的根本原因 —— 不是随机化不够随机，
是**可随机的维度只有一个**（选哪个模板）。

补了纵向之后，关卡图能写：

```
node hall    template=part_hall      after=combat_a   ← 横向
node corner  template=part_corner    after=hall       ← 横向
node shaft   template=part_tower     below=corner     ← 纵向
node landing template=part_landing   below=shaft      ← 纵向
node combat_b template=room_04       after=landing    ← 转回横向
```

形状从「一条线」变成「一段抬升 + 一口竖井 + 落回地面」。
**上去和下来不再是同一条路** —— 这是 DC 的基本节奏。

## 14.2 四处改动

### ① 生成器认识 `U` / `D`

`gen_room_terrain.gd`：

| 位置 | 改动 |
|---|---|
| 字符表 | 新增 `CH_DOOR_U/U`、`CH_DOOR_D/D`，进 `VALID_CHARS` |
| `_validate` | U 必须在第 0 行、D 必须在最后一行；各最多 1 格 |
| `_door_reachable` | **加 `grid` 参数**：U 往**下**找站面、D 往**上**找 |
| `_build_doors` | 从"只看左右两列"改成**扫全部格**；碰撞盒按方向换尺寸（横 60×140 / 竖 140×60） |
| `_build_spawns` | 新增 `SpawnFromUp` / `SpawnFromDown`，走新的 `_make_spawn_vert` |

两处容易写反的地方，都写进了注释：

- **D 门的可站面在它上方**。按「门格往下找两格」的旧口径判 D，下方是地图外，
  会永远判不可达 —— 这不是严格，是判错了。
- **纵向 spawn 不能复用横向的 `_make_spawn`**。那个函数沿**同一行**往左右退，
  放在顶行会横着扫出去，全是墙。所以拆成 `_make_spawn_vert` 沿列找。

### ② 四个垂直零件

`world/tools/build_parts.py` 生成，设计放在 Python 矩形列表里，ASCII 仍是唯一产物：

| 文件 | 尺寸 | 门 | 用途 |
|---|---|---|---|
| `part_hall` | 28×30 | L / R | 横向主链上的挑高厅，七层之字形平台 |
| `part_tower` | 18×42 | U / D | 纯垂直竖井，**九层楼板 + 交错缺口** |
| `part_corner` | 24×28 | L / D | 横向转纵向（走到洞往下掉） |
| `part_landing` | 24×26 | U / R | 纵向转回横向（掉进来，走到右门） |

`part_landing` 是被"缺零件"逼出来的：只有 corner（L→D）和 tower（U→D）时，
垂直段只能一路向下到终点，整关会变成**一部下不来的楼梯**。
必须有「U 进 R 出」才能把竖井接回主脊。

### ③ 拼装器支持 2D 布局

`gen_level.py`：

| 函数 | 改动 |
|---|---|
| `parse_graph` | 支持 `below=`，转成 `link="v"` |
| `Template` | 从"只有 L/R"改成四门契约，`has_in(link)` / `has_out(link)` |
| `layout` | 纵向：`row = parent.row + parent.rows`，`col = parent.col + D列 − U列` |
| `merge` | 门格按 `is_first` / `is_last` 决定保留还是变洞 |
| `punch_seams` | 横缝挖 2 列 × 3 行；竖缝挖 **3 列 × 2 行**（尺寸对调） |
| `verify` | 横缝验**行**，竖缝验**列** |

**纵向缝合比横向少一个约束**：横向要行对齐（差一行就是 48px 的坎），
纵向只要列对齐 —— 人是从上门**掉**进来的，不是走过去的。

### ④ 一个藏在 merge 里的坑

拼完之后生成器判 `FAIL: 门 (0,26) 不可达`。查了半天：那扇门好得很。

真凶是 **room_01 内部有一个 `P`（它作为独立房间时的出生点）**。
拼进整关后 `P` 被原样保留，而生成器的可达性把 `P` 当成**全关起点** ——
于是「玩家在 atrium 出生，走不到左上角的 L 门」。

修法：`merge` 时非第一间的 `P` 一律丢掉。注释里记了这次踩坑，
因为「错误信息指向的位置和真正的问题无关」是最费时间的一类。

## 14.3 机器人也需要升级

L7 的机器人原来只会「一路向右 + 卡住就跳」。在竖井里它直接失效：

| 症状 | 根因 | 修法 |
|---|---|---|
| 卡在楼板右端，反向 205 次原地不动 | 塔的缺口左右交错，只会向右走的人永远到不了 | 加 `_descend`：撞墙反向，左右扫 |
| 反向之后还是不动 | **释放的是新方向的键**，旧方向还按着，两键抵消 | 释放旧方向 |
| 一直在楼板边缘上蹿下跳 | 塔里跳 4 格远，正好**跃过 2 格宽的缺口** | 竖井里禁止跳，下落只能靠走 |
| 刚掉一层就判"到底" | `y >= y_mark - 2` —— 屏幕 y 向下增大，下落时恒成立 | 改成 `y <= y_mark + 2` |
| 掉到楼板边被粘住 | 自动抓边（给玩家的手感辅助） | 验证结构时关掉 `_ledge_assist_used` |

那句「释放的是新方向的键」值得单拎出来：这是**写测试代码时最容易犯的错**，
因为它的表现不是报错，是"机器人看起来很努力但没进展"。反向验证救了我一次 ——
如果不做反向验证，我会以为"关卡过不去"，然后去改关卡。

## 14.5 反向验证：两条判据都必须能 FAIL

把 `corner→tower` 的竖缝（c91-c93 / r31-r32）用 6 格实心堵死：

|---|---|
| `test_level_gen` L4 | **FAIL**「堵了 6 格」 |

第三条是这一轮最有价值的发现。

## 14.6 生成器的可达性一直在"穿墙"

堵死竖缝后，生成器依然判 PASS。查 `_can_move`：

```gdscript
# 旧代码：只检查起点那一行的横向阻挡
for c in range(from.x + step, to.x, step):
    if _is_solid(grid, from.y, c):
        return false
```

这条边是「从 r30 往下掉 5 格到 r35」，墙横在 r31-r32 —— **一列都没检查**。

第一版修法是"沿连线逐行检查"，结果矫枉过正：正常跳跃也判死，
可达格从 873 掉到 414，`room_01` 单房直接 FAIL。

正确的口径是**只查人真正经过的那一列**：

- 下落（`to.y > from.y`）→ 查**落脚列**（最终落到哪儿，那一列中间不能有实心）
- 上升（`to.y < from.y`）→ 查**起跳列**（人从哪儿往上蹿，那一列头顶不能有实心）
- 横向 → 只查起点那一行（人不换高度）

修完，六个房间全部回到 PASS，而堵死竖缝能正确报错。

# 15 · 第八次：支线 / 节点级随机 / 缩尺寸

三条一起做，因为它们互相咬：没有 `repeat` 就没有"房间数由种子决定"；
没有 `branch` 就没有"主脊旁边挂一间"；而这两条都会把关卡撑大，
所以缩尺寸不是独立的收尾，是同一批改动的第三条腿。

## 15.1 支线：`branch=1`

**语义**：节点挂在主链某间的 `U` 门下面，走完**回到原地**，不接续主链。
这是 DC 关卡图的最小完整形态 —— 主脊 + 岔路。

表里三个新键，每条都配一条校验（校验写在 `parse_graph` 里，报错就退出）：

| 键 | 含义 | 校验 |
| --- | --- | --- |
| `branch=1` | 这间是支线，不接续主链 | 必须用 `below=`（纵向挂在下面）；不能带 `repeat` |
| `repeat=a-b` | 放 a~b 间，个数由种子定 | 展开后必须唯一 `after` 链 |
| `at=<col>` | 支线在父房间宽度内的横坐标 | 夹在父房间列范围内 |

**候选模板必须"有上门、无下门"**：支线是从上往下钻的，带 `D` 就变成
"还有下一间"，语义就串了。现在池子里只有 `part_pocket` 符合。

**接缝（seam）在 layout 里算，不在零件里算。**
支线的缝形状不固定：从父房间的可站面下一行，一直挖到口袋的天花板。
只有 layout 知道"挖到哪儿为止"，所以 `it["seam"]` 由 layout 填，`punch_seams` 只负责按图挖。

```python
seam = {"kind": "v", "col": dc, "half": 1, "rows": list(range(top, row + 1))}
```

`half=1` → 挖 3 格。**不能挖 5 格**：生成器的可达性模型只认 4 格跳距，
5 格宽的洞会被判成"整个右半关是孤岛"（实测报出 649 格孤岛）。
这一条不能靠"玩家其实跳得过去"兜底 —— 图纸说能过、判据说不能过，
那就是判据错了，而判据是给以后的房间用的。

## 15.2 节点级随机：`repeat=a-b`

```
node combat_a tag=combat template=room_03,room_02,part_hall repeat=1-2 after=entry
```

个数由 `node_rng(seed, id + ":repeat")` 决定。这一步做完，
"房间数"才第一次不是常数。

**踩到的坑（值得记下来）**：展开后的 `after` 必须逐间接龙，
第 2、3 间要指向前一个展开体，而不是都指向原始 `after` ——
否则两间房坐标完全重合（`combat_a` 和 `combat_a2` 都在 `(26,14)`）。

接龙之后又引出第二个坑：后面有一趟"把 `after` 改指向最后一次展开"的修正，
它会把接好的链全改成指向自己。所以展开体加 `_chained` 标记跳过那一趟。

第三个坑更隐蔽：`expand_repeat` 对非 `repeat` 节点原来是 `out.append(n)`，
直接把输入图里的对象放进输出。于是"改 `after`"改的是**原图**，
`--variety` 跑第二个种子就 `KeyError: 'combat_a2'`。
现在一律 `out.append(dict(n))`，并写了注释「共享可变状态，一次就够踩」。

**判据 `--variety`**：跑 5 个种子，断言

- 模板序列 ≥ 4 种（不能永远是同一条房间串）
- 房间数或总宽 ≥ 2 种（结构真的变了，不是只换了零件）

实测：

```

seed 7       房间 12（主链 11）  258×112 → 258×75
seed 42      房间 12（主链 11）  258×112 → 258×75
seed 2026    房间 13（主链 12）  284×112 → 284×75
seed 99991   房间 12（主链 11）  258×112 → 258×75
模板序列 5 种 / 宽度 2 种 / 房间数 2 种 → ✓ 不同种子产出不同结构
```

### 缩尺寸的第一个副作用：撞头

砍高度时我把大厅顶层台从 r5 抬到 r2，画出来一切正常 ——
平台是橙色线，看得见，能站上去。但**人站不直**：

```
玩家高 64px = 1.33 格
脚踩在台面上时，身体会伸进上面那一行的 16px
台面在 r2 → 头顶只剩 r1 一行（48px）→ 身体被挤
```

平台存在、玩法不存在。所以给零件构建器加了一条净空判据
（`build_parts.py` 的 `Grid.check_headroom`）：

> 凡是「脚下是实心、自己这格是空」的位置，头顶那格不能是**墙** `#`。

只查墙、不查平台 `=`：`=` 是单向平台，从下往上穿过去不挡人，
头顶压着一块单向平台顶多是视觉上贴着头皮；头顶是墙就一定会挤。
现在六件零件全部通过，任何一件改出"平台画得出来但站不直"直接 `AssertionError`。

同一批还修了口袋的底层台：原来在 r7，离地板只有 1 行（48px），
平台下面那 9 格地板就废了 —— 这是一个"战斗盒"，底部被劈成两半就不是盒了。
挪到 r6，下方留 2 行（96px > 64px），可以从底下走过去。

## 15.4 本轮最重要的一条：口袋为什么只能做成梯台竖井

这一条是**算出来的**，不是试出来的。

```
单跳高度 = v0² / 2g = 890² / (2 × 1940) = 204px = 4.25 格
想走的路 = 口袋比洞口低 3 格(144) + 身高 1.33 格(64) = 208px
208 > 204  →  「掉到底再爬回来」的口袋，物理上不可能
```

也就是说：只要口袋比父房间地板低 3 格以上，人就永远出不来。
第二版口袋我让机器人试了 2700 帧、换了 58 次向，卡在第二级平台上 ——
**不是它笨，是解不存在**。

所以顶层台面必须**在洞口里面**：

- 位置：`plat(8, 10, 1)` —— 洞口那一行的正下方；
- 宽度：**必须等于洞宽**（3 格）。宽一格，站在两端的人头就顶进父房间的实心地板；
- 低一格：往外跳只剩 12px 余量，跳得出洞口却挪不上地面。

往下靠「下 + 跳」逐个下穿（平台全部盖住洞口那几列），
往上靠原地跳 —— 两个方向都不需要横向微操。

**反向验证（做了）**：拆掉口袋的顶层台 → `L8 从支线爬了出来` FAIL
（30 秒耗尽停在 y=5151，目标 ≤4668）+ `L7 走到最后一间` FAIL（卡在 x=7538）。
装回去全绿。判据能红，才算判据。

# 16 一间房是什么

这一节定的是**术语**。前面十几节里「房」「房间」「屏」混着用，导致后面所有尺寸讨论都在打滑。

## 16.1 一句话

一间房 = **一个 `cols×rows` 的字符矩阵 + 一份门契约**。

## 16.2 它有四种身份，只在三种里存在

| 身份 | 落在哪 | 谁读它 |
|---|---|---|
| 设计期 | `world/rooms/blueprints/*.txt` | 人（手画） |
| 拼装期 | `level_01.graph` 的一个 node | `parse_graph` / `expand_repeat` |
| 世界期 | `layout.json` 的 `rooms[]` 一项，带 `(col,row)` | `layout()` / `punch_seams()` |
| **运行时** | **不存在** | — |

运行时不存在这件事要说清楚：`Level01.tscn` 有 391 个节点，层级只有
`Level01 → Terrain → WireBackdrop / Solids → Box0..BoxN`。十二间房的地形被摊平成
同一张位图和一堆碰撞盒，**没有任何节点代表「一间房」**。

代价是明确的：进房触发事件、房间级迷雾（地图揭示）、房间级存档，这三样现在都做不了。
要做就得补一层「用 `(col,row)` 反查 `layout.json`」的运行时归属判定。

## 16.3 三条判据（缺一不可）

| 条件 | 代码位置 | 反例 |
|---|---|---|
| 一个非空字符矩阵 | `Template.__init__` 读 `grid` | 空文件 |
| 至少一个门字符，且落在边界列/行 | `find_door(grid, "L"/"R"/"U"/"D")` | 封闭盒子接不进去 |
| 被 `layout()` 赋 `(col, row)` | `layout()` 返回的 `inst` 项 | 只躺在磁盘上的蓝图 |

## 16.4 什么不算一间房

- **接缝（seam）**：两间之间被挖开的那几格。由 `layout()` 预算、存在 `it["seam"]`，
  不归任何一间房。支线的缝形状不固定（从父房间可站面下一行一直挖到口袋天花板），
  只有 layout 知道「挖到哪儿为止」。
- **房间内部的平台**：`part_hall` 的六层之字是同一间房的内部结构，不是六间房。
- **一屏**：`room_02` 是 26×15，正好等于 1280×720 的格数，这是巧合（老房间按一屏画的）。

## 16.5 三种拼接的几何

| 连接 | 规则 | 是否重叠 |
|---|---|---|
| 横向 | `col = 父.col + 父.cols`；门行按**站面行**对齐 | 否 |
| 纵向 | `col = 门列 − 子.door_u[0]`；只对齐列，不对齐行 | **是** |
| 支线 | 同纵向，且必须「有上门、无下门」 | **是** |

横向这条有个踩坑记录：早先试过重叠一列，结果只剩 1 格宽的缝（48px 对 34px 碰撞盒），
「能过但一直蹭墙，看起来像两堵墙夹一条缝」。改成并排 + 事后挖开两列，才是 2 格宽（96px）。

纵向重叠的实例：`shaft` col110..127 落在 `corner` col106..129 之内；
`pocket` col140..157 落在 `combat_b` col136..161 之内。

## 16.6 屏 ≠ 房：§15.7 那条「目标定错了」的答案

```
屏          = 1280×720 = 26.7 × 15 格
room_02       26×15 = 1.00 屏 × 1.00 屏
part_gate     44×16 = 1.65 屏 × 1.07 屏
part_tower    18×24 = 0.67 屏 × 1.60 屏
```

屏是显示单位，房是设计单位，**两者没有固定换算**。用「屏宽」当约束，等于给一个
18~44 格浮动宽度的对象定一个固定总和 —— 任何房间数变化都会被它误判成超标。

所以 §15.7 第 2 条成立：不是目标太高，是**单位错了**。
宽度约束应该写成「单间 ≤ 28 格，总宽 ≤ 240 格」，不写「6~8 屏」。

## 16.7 缺的一层：节奏

现在一间房只有空间参数（`cols×rows`），没有节奏参数。

`room_02`（26×15，2 敌）和 `part_hall`（28×24，六层平台）都叫一间房，
但前者约 15 秒、后者约 40 秒，玩法量差 2.6 倍。DC 有两层：**room（空间）**与
**segment（节奏）**。我们只有前者，所以 `repeat` 调的是空间数量、玩家感知的是节奏，
两个指标对不上 —— 这就是「房间数下限」这个指标一直不够用的根因。

补法：`PARTS` 元组加第四项 `beats`（这间房提供几个强度峰），`emit` 写进 `layout.json`，
关卡图约束从「房间数 ≥ 9」改成「总 beats ≥ N」。

# 17 门：层内小尺度，过渡区才是小地图

## 17.1 错在哪

`part_gate` 是 44×16 的房，满高闸门 r1..r22（22 格），开关在 13 格高的台阶顶，
门后是唯一主路（gate → shop → boss），通过耗时约 40 秒。

错不在「设计了门」，在**把门做成了结构**：它是 graph 的一个节点，所以必须占一整间房；
门后是主路，所以必须爬上去才能过。

DC 把门当成**房间内部的一个角落**，所以它既不占结构、也不挡主路。

## 17.2 DC 的八类门（wiki 原文分类）

| 门类 | 位置 | 尺度 | 门后 | 需要 |
|---|---|---|---|---|
| 木门 | 层内 | 1~2 格 | 隔断（挡视线/挡敌人） | 随时开，或砍碎 |
| 机关门 Z | 层内 | 1~2 格 | 一段通道 | 打**旁边**的开关 |
| 金门 | 层内 | 1~2 格 | 一件装备/卷轴 | 付钱，或砍碎换诅咒 |
| 钥匙门 | 层内 | 1~2 格 | 图纸/贵重物品 | 找钥匙 |
| 限时门 | **过渡区** | — | 奖励房 | 时间达标 |
| 完美门 | **过渡区** | — | 奖励房 | 连杀无伤 |
| 细胞门 | **过渡区** | — | 奖励房 | BSC 难度 |
| Boss 门 | Boss 房 | — | — | 打完 Boss |

关键在 wiki 对机关门的那句原文：「must be unlocked by hitting a **nearby** switch」。
**nearby** —— 开关在门旁边，顺手一下，全程 3 秒。

**层内那四种门全是「1~2 格宽、门后一个小间」**。所谓「门在独立小地图」对应的是
限时门 / 完美门 / 细胞门这三类：它们确实只存在于两个 biome 之间的过场里。

所以准确的说法是：**层内没有「关卡闸门」，但层内一直有「1~2 格的小门 + 小间」**。
这两件事不能混。

## 17.3 四维错位

| 维度 | DC | `part_gate` | 倍数 |
|---|---|---|---|
| 门高 | 2~3 格 | 22 格（满高） | 7~10× |
| 开关位置 | 门旁 | 13 格高台阶顶 | 爬 5 段 |
| 门在哪里 | 房间角落 | 唯一主路 | — |
| 门后 | 一个小间 | 半张关卡 | — |
| 通过耗时 | 3~5 秒 | 约 40 秒 | 8~10× |

## 17.4 判定：`part_gate` 作废

**不改的**：「开关 → 门」这个机制本身是 DC 真实的（Z door），保留。

**三条铁律**：

1. **门不能占节点**。它必须是房间内的一个角落，不占宽度、不进 graph。
2. **开关必须在门旁**。站在地面能碰到，不能爬。
3. **门后只能是奖励**。主路上永远没有「需要条件才能通过」的东西 ——
   主路不通就是玩家卡死，这是设计事故，不是难度。

## 17.5 替代：`niche`（层内小间）+ 过渡区（独立场景）

**`niche`**：3 格高的小门 + 门旁 2 格开关 + 6×5 奖励小间，镶在战斗房的侧墙上。
不占 graph 节点、不占关卡宽度。每层撒 2~3 个。

**过渡区**：层与层之间的小场景，放限时门 / 完美门 / 细胞门 + 下一层出口选择。
它是独立场景，**不进本关 layout**。这一步还没做，属于后续。

## 17.6 宽度：删掉闸门节点后自己就达标了

```
现状              258 格 = 9.68 屏
删 gate（44 格）  214 格 = 8.02 屏   ← 落进 6~8 屏
repeat 全取 1     188 格 = 7.05 屏
combat_b 取 2     240 格 = 9.00 屏
```

主链房间数：11 → 9~11 间（实测 10），下限 9 仍满足。

那 44 格里本来就没有玩法，只有一段爬台 —— §15.7 第 4 条说的「门右侧 6 格空走廊」
只是症状，**整 44 格都是空的**。
