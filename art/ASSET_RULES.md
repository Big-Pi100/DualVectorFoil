## 0. 为什么要单独有一套使用规则

一张砖块画得再好，如果不知道它和谁相邻、重复第 7 次会不会露馅、换主题时要不要重画，
那它就不是资产，是一张图。FC 马里奥的产能优势不在画工，在于**每张图都预先定义了插槽**：

- 一块砖 = 16×16，永远 16×16，绝不为了某个场景加两像素；
- 地面 = 左端 + 中间×N + 右端，中间段首尾同边，所以能铺任意长度；
- 同一形状换调色板就是地下关、城堡关、夜关 —— **不重画，只换色**；
- 装饰（云、灌木）是独立小件，可以摆在任意格点上，不参与碰撞网格。

它的每一条都是**可判定的**：尺寸是不是网格整数倍、接缝像素是否相等、换色前后轮廓是否一致。
本文件把这套判据落到本项目的资产上，并且**写成能跑的命令**，不靠评审时的眼力。

## 1. 资产按「角色」分类，每类有自己的验收断言

资产不是按"好看程度"验收的，是按**它在关卡里扮演什么零件**验收的。角色写在
`art/approved/manifest.json` 里（缺省按目录推断，`tile_*` 必须显式写）。

| role | 是什么 | 本作实例 | 必须满足 |
| --- | --- | --- | --- |
| `tile_cap` | 只出现在两端的收口件 | `ground_left` `ground_right` | 宽高是 `TILE=48` 整数倍；外侧圆角收口 ≤ 20px；**内缘**与 `tile_mid` 逐像素相等 |
| `tile_mid` | 可无限重复的中间件 | `ground_mid` | 宽高 48 整数倍；**首尾同边**（左列 == 右列）；回文（正放 == 翻转）；体内无整行透明 |
| `sprite` | 角色 / 敌人，单帧站姿 | `player_*_sprite` `enemy_*_sprite` | 帧框 340²（敌人 128²）；**脚底基线**固定（角色 y=295）；一态一图，不做多帧插值 |
| `prop` | 只摆不拼的立体摆件 | `terrain_stone_block` `terrain_stone_pillar` … | **禁止进 tilemap、禁止当地面**（见 §4） |
| `fx` | 一次性特效 | `fx_hit` `fx_jump_puff` … | 已裁紧 bbox，无洋红/白边残留 |
| `ui` | 界面件 | `ui_hud_frame` `ui_heart_icon` … | 四边可切，九宫格拉伸不变形 |

**同一张图只能有一个角色。** 想让一块石头既是平台又是装饰，就出两张 —— 因为它们的
验收断言冲突（平台要顶边平、装饰要轮廓生动）。

## 2. 拼接语法：底板 = 左端 + 中间×N + 右端

### 2.1 公式

```
width = cap_w × 2 + mid_w × N        (N ≥ 0，整数)
```

本作参数：`cap_w = 96`（2 TILE）、`mid_w = 384`（8 TILE）、`height = 144`（3 TILE）。

| 用途 | N | width | 说明 |
| --- | --- | --- | --- |
| 主地面 | 2 | 960 | = 一屏，正好 |
| 中平台 | 1 | 576 | |
| 小台阶 | 0 | 192 | 两块端点直接对接，也合法（接缝同样逐像素相等） |

**没有第三种长度。** 576 到 960 之间要一档，就得再加一个尺寸的 `tile_mid`，
不是把中间段拉宽 —— 拉伸过的接缝不再逐像素连续，等于把规则废掉。

> 执行这条规则的拼接器是旧原型的 `ground_strip.gd`（非法长度 `push_warning` 并留空，
> 不偷偷缩放），**已随骨架移进 `legacy/godot_prototype_2026-11-27/scripts/`**。
> 2026-11-27 并进来的完整 Godot 工程**还没用这套底板** —— `world/rooms/*.tscn` 的
> `Floor` 目前是 `ColorRect` + `grass_decor` 贴片。规则本身没作废，是工程侧待接。

### 2.2 三条接缝为什么必然不露

手绘资产没法靠"画的时候对齐"来保证首尾同边，所以用**镜像构造**把缝变成恒等式：

```
L = 前 96 列
M = 紧接着的 192 列     （与 L 在重采样图里相邻，所以 L 的右缘 == M 的左缘）
mid = M + mirror(M)      → 首尾同边，且整体回文
R = mirror(L)            → 左缘 == L 的右缘 == mid 的左缘
```

于是 `L|mid`、`mid|mid`、`mid|R` 三条缝**逐像素相等**，不是"看起来差不多"。
`slice_ground.py` 每次都实测这三条缝，`asset_rules_check.py` 可以随时复检。

### 2.4 纵向（Y 轴）：现在只有横向同边，竖向是空的

§2.2 的镜像构造只保证**左右同边**（左列 == 右列），所以底板能横向无限拼。
但它**不保证上下同边**，于是：

```
底板叠两层  →  出现一条横向缝（144 的整数倍处）
底板当竖井侧壁  →  草皮朝上，竖过来草就在侧面，读起来是"塌了"
```

恶魔城式地图是 X/Y 双轴：主干是竖井、树冠是混合、房间高 11–22 格
（`docs/gdd/04 §3`）。**这一块现在一张资产都没有。** 缺什么、怎么算尺寸，
见 §8。在纵向件出来之前，关卡只能做横向房 —— 这是硬缺口，不是排版问题。

纵向件的拼接语法与横向同构，只是把"左右"换成"上下"：

```
高 = vcap_h × 2 + vmid_h × N          竖井 = 左右两面墙 + 顶底收口
宽 = wall_w × 2 + 内空                  内空 ≥ 5 格（240px）才放得下角色与敌人
```

### 2.3 「无缝」的判据不是一个常数

蜡笔是高频纹理，图内**相邻两列本来就差几十**。拿 `差 > 8 就算缝` 去卡，
卡的是画风不是缝，手绘图一张都过不了。

正确判据是**同口径比较**：

```
基准 = 中间图内相邻两列的最大通道差的 95 分位
接缝 = 接缝两侧列的最大通道差
通过 ⟺ 接缝 ≤ 基准
```

即「接缝不比图内任意相邻两列更跳」。实测本作 `基准 = 119`，`L|mid = 110 ≤ 119` ✓，
`mid|mid = 0`（镜像构造，恒等）✓。这个数字换成别的图会变，判据不会。

## 3. 复用规则：一次画，多次用

复用不是"凑合着用"，是**预先设计好复用点**。本作允许四种，按优先级：

| # | 手法 | 说明 | 本作是否在用 |
| --- | --- | --- | --- |
| R1 | **镜像** | 右端 = 翻转的左端 | ✅ `ground_right` = `mirror(ground_left)` |
| R2 | **重复** | 中间段无限拼 | ✅ `ground_mid` |
| R3 | **换色** | 同形状换色系，出另一套主题（地下/夜/雪）**或另一个状态（怪 ↔ 原住民 ↔ 清完的地）** | ✅ 敌人 `duo_state.py` / `ally_from_gen.py`；**场景 `scene_state.py`（11-27）** |
| R4 | **缩放** | 只允许整数倍，且只用于 `prop` | ⚠️ 受限：角色/敌人**不缩放**（`ART_GUIDE §12.2.1`） |

R3 是马里奥产能的真正来源：一套地形图 + 三套 8 色调色板 = 三个世界。
本作的地形已经收敛成「草地」一套，换色出「地下」只需要一个脚本 + 一次门禁抽样。
**这句 11-26 写下时是待办；11-27 由 `scene_state.py` 兑现（见 §3.2）。**

### 3.1 R3 的第二条用法：一个造型，两个状态（2026-11-27 白哥定）

白哥定：**原住民就是树上的动物，有怪物和原住民两种形态**
（史莱姆 ↔ 小精灵、暗黑蝙蝠 ↔ 粉色蝙蝠），要求**完全同样造型的两套色系**。

这条如果照字面执行 = 每个敌人画两遍。但 R3 已经给了答案：**同形状，换色系。**
两者的区别只是"换色的目的"：

| | 主题换色（地形） | **状态换色（敌人）** |
|---|---|---|
| 换来干什么 | 换一张地图的主题 | 换同一只生物的**健康状态** |
| 谁决定 | 关卡主题 | 玩法（能不能招安） |
| 工具 | 待写 | ✅ `art/tools/duo_state.py` |
| 输出命名 | `*_underground` | `enemy_<名>_ally_00_sprite`（现状是 `_sprite` = dark） |

**可判定的定义（八条，缺一条就不成立）**：

| # | 断言 | 不做会怎样 |
|---|---|---|
| 1 | 尺寸相同 | — |
| 2 | **轮廓 IoU ≥ 0.95**（换色版恒为 1.000） | 低于这个数就是另一只了 |
| 3 | 生成版的半透明边缘不得糊 | 边缘发毛，缩放时露馅 |
| 4 | **主体色相位移 ≥ 60°** | 少于这个数人眼判为「同色深浅」= 褪色 |
| 5 | **饱和不低于原图 × 0.85**（换色版）／ **≥ 0.40**（生成版） | 砍饱和 = 蒙白纱，读作「变淡」 |
| 6 | **明度对比度不低于原图 × 0.85**（换色版） | 对比度塌 = 蜡笔笔触被洗平 |
| 7 | 无彩色像素（S<0.08）不参与换色 | 白高光/黑描边是明暗骨架，染色会脏 |
| 8 | **落在各自色带内**（暗黑态 215–322／解放态四条自然带）＋ 解放态明度 ≥ 0.60 | 两态就没有"明显的风格区分" |

第 1–8 条由 `duo_state.py --check` 执行，**生图产线走同一份断言**，不靠眼力。
第 2 条原本是「alpha 逐像素相同」，2026-11-27 之后放宽为 IoU —— 原因见 §3.1.4
（眼睛必须重画，而重画必然让 alpha 差几百个像素）。

### 3.1.1 「褪色 ≠ 换色」—— v2 的错，必须留档

v2 用的是 `v' = 1−(1−v)(1−lift)` + `s' = s×0.42`（提亮 + 压饱和）。实测三张：

| 敌人 | Δ色相 | Δ饱和 | 明度对比度 |
|---|---|---|---|
| slime | +5.4° | −58% | 0.95 → 0.43 |
| bat | +5.5° | −58% | 0.95 → 0.43 |
| spike | +5.4° | −58% | 0.78 → 0.35 |

白哥原话：「**你只是让精灵图整个颜色变淡了，并没有真的改变颜色，是褪色不是变色。**」

根因在公式而不在参数：`1−(1−v)(1−lift)` 是**往白里推**，暗部被抬得比亮部多
（v=0.28→0.68，v=0.47→0.76，差值 0.19→0.08），对比度一塌，蜡笔肌理就没了，
剩下的淡色只能读作"蒙了层白纱"。

> **褪色 = 往白推**（压缩对比度 + 降饱和 + 色相几乎不动）
> **换色 = 换色相**（对比度与饱和另算，明度只用加法平移）
> 两者在公式上长得像，结果完全不同。**判据是色相位移，不是亮度。**

### 3.1.2 v3 的做法：色相分区映射

先用 `--probe` 量出 dark 版的色相锚点（主体 / 背光 / 点缀各在哪个区间），
再给每只敌人配一张**色卡**，把每个锚点搬到**明确指定的目标色相**上：

| 敌人 | 主体锚点 | → 原住民色 | 其他锚点 |
|---|---|---|---|
| slime → 小精灵 | H300-330 淡紫 60% | **淡蓝 H208** | 背光冷紫 H250-290 → 深蓝 H198；眼嘴暗红棕 → 蜜金 H44 |
| bat → 粉翼蝠 | H250-270 深紫蓝 | **樱粉 H342** | 紫高光同色相只提亮（靠明暗分层次）；金黄眼保留 |
| spike → 绒刺球 | H210-240 亮蓝 60% | **薄荷绿 H148** | 红刺 → 暖橙 H28（身体↔刺仍差 112°，刺不糊进身体） |

明度只用**加法平移**（`v+add`）：平移整段、区间宽度不变，对比度天然保住；
乘性/往白推按 v 缩放，暗部被抬得比亮部多，层次就糊了。

**眼珠同色化**：黑眼珠原被第 7 条当"无彩色"跳过，结果绿身子配一双死黑眼。
判据用**到 alpha 边缘的距离**（`_erode` 3 次）区分：贴边的黑 = 描边（保留），
内部的黑 = 眼珠（换成目标色系的深版）。不动形状、不动 alpha。

**换色产线做不到的一半**（这就是后来必须加生图产线的原因，见 §3.1.4）：

色系只能表达**「同一只生物的状态」**，不能表达**「另一种气质」**。v3 实测：

| 敌人 | 换色后 | 颜色成立？ | 「可爱」成立？ |
|---|---|---|---|
| 小精灵 | 淡紫 → 淡蓝，笔触完整 | ✅ | 🟠 蓝身金眼很灵，但眼睛形状还是扁椭圆 |
| 粉翼蝠 | 深紫 → 樱粉，粉得很正 | ✅ | 🟠 粉是好粉，**凶的还是那双斜挑的黄眼** |
| 绒刺球 | 蓝+红刺 → 薄荷绿+橙刺 | ✅ | ❌ **怒眉原封不动**，绿刺猬照样在生气 |

结论：**色系管状态，眼睛管情绪。**

「凶」来自三处形状特征：**怒眉**（斜向下的粗黑楔）、**竖瞳**、**斜挑眼形**。
这三样都不在 RGB 里，色卡碰不到。解决办法见 §3.1.4（最后走了生图，像素 patch 四版全废）。

### 3.1.3 两套色系（2026-11-27 白哥定：定下来，后续才容易做）

白哥原话：「**需要把暗黑状态的色系和解放状态的色系定下来，做明显的风格区分，这样后续就更容易做。**」

先排除一条错路：**风格区分不能靠"亮一点/暗一点"**。
实测 slime 的暗黑态 V 就已经 0.71（淡紫，本来不暗），spike 两态 V 都是 0.73。
明度和饱和都分不开。**唯一能分开的是色相。**

| | **DARK 暗黑态** | **ALLY 解放态** |
|---|---|---|
| 主体色相带 | **H215–322** 紫／靛 | **四条自然带，同带最多 2 种** |
| | | 暖金 H20–62 · 嫩绿 H88–175 · 水蓝 H180–212 · 樱粉 H325–355 |
| 为什么是这个带 | 被注入黑色素 ⇒ 不管原物种什么色，一律发紫。**这是"被改写"的色相指纹** | 原住民是活物，用自然色。四带分开 ⇒ 一眼看出"这棵树有很多种居民" |
| 饱和 | 0.20–0.45（中低，显病态） | **≥0.40**（低于读作灰；v2 是 0.14） |
| 整体明度 | 不限（slime 0.71、bat 0.56 都合法） | **≥0.60**（不许压暗） |
| 暗部 | 可压到 V<0.20（墨堵死的地方） | **不压黑**，那是"活着"与"被堵"的分水岭 |

**两条带相邻但不重叠**（水蓝带上限 212 < 暗带下限 215），所以判定互不打架。
`duo_state.py` 用 `DARK_HUE_BAND` / `ALLY_HUE_BANDS` / `ALLY_MIN_SAT` / `ALLY_MIN_V`
把这四条钉成断言，`--check` 时逐条验；`--palette` 出两套色系的色相带总览图。

**已验证的分配**（后续新敌人按这个表往下接，别重复占色）：

| 物种 | DARK 实测 | ALLY 目标 | 占的带 | 产线 |
|---|---|---|---|---|
| 史莱姆 → 小精灵 | H306 | **H206 水蓝** | 水蓝 | 换色 |
| 暗黑蝙蝠 → 粉翼蝠 | H263 | **H342 樱粉** | 樱粉 | 换色 |
| 刺球 → 绒刺球 | H225 | **H150 薄荷绿** | 嫩绿 | 换色 |
| 纸屑群 → 纸虱 | H272 | **H36 麦纸金** | 暖金 | 生图 |
| 墨渍 → 露珠虫 | H261 | **H196 露珠蓝** | 水蓝（与 slime 同带） | 生图 |

**为什么 5 个敌人只有 4 条带**（2026-11-27 补 5 种敌人时撞上的）：

MVP 敌人 5 种，自然色带 4 条 —— 一开始写的是"每只占一条不重复"，第 5 只就没位置了。
放宽成**「同带最多 2 种，且必须是近亲」**，而不是加第 5 条带：

- 加第 5 条只能从现有四条里切一刀（比如把嫩绿拆成嫩绿+青碧），切出来的两条差 ~25°，
  肉眼分不出，等于假装有 5 种颜色 —— 比承认同带更难维护。
- 同带的前提是**近亲**：小精灵（软体，`slime`）与露珠虫（水滴，`ink`）都是"柔软、水生、
  半透"的东西，同属水蓝带不矛盾；反过来若把蝙蝠塞进水蓝带，玩家会读成"这两只是一家"。
- 于是这条带的语义从"每只一个颜色"变成**"每个色系一族"** —— 局限更小，也更好扩展。

**必须承认的一条硬冲突（2026-11-27，未解决，等白哥定）**：

纸类原住民的固有色是**米白**（纸本来就是白的），但解放态有硬下限 `S≥0.40`
（`ALLY_MIN_SAT`，为的是不读成"灰"）。两条一撞，纸虱只能做成**麦纸金 H36 / S0.44**，
在实战尺寸下读作"暖褐纸片群"，比"晒过的白纸"脏一档。

三条出路，各有代价，没有免费的：

| 方案 | 代价 |
|---|---|
| A. 维持现状（麦纸金） | 纸虱是五个里最暗的一只；"纸是白的"这个直觉要玩家自己补 |
| B. 给"纸类"开一条低饱和豁免带 | 断言从"必须有饱和"变成"按材质分档"，规则复杂度上升；且以后人人想申请豁免 |
| C. 换物种（纸虱 → 会变色的虫） | 改动 `02 §5.3` 的物种列与「纸质=可招安」这条分类根基，牵连最大 |

**当前取 A**，因为它是唯一不动规则的；若白哥觉得纸虱看着不对，再走 B。

**新增敌人的做法（四条，不用重新发明）**：

2. 落盘用 `ally_from_gen.py --dark`（不是随手贴）：它按画布约定放（内容高 48 / 脚底 y=87 / 居中），

### 3.1.4 眼睛：像素 patch 试了四版全废，最终走生图

白哥 2026-11-27：「**手功能扣当然最好，但是如果扣不了就生成也可以。**」

先试"手抠"（坐标人工从 16 倍密网格图读，算法重绘）。四版全废，留档：

| 版 | 做法 | 结果 |
|---|---|---|
| v1 | 三只共用一函数 + 内接椭圆覆盖整个眼睛 | 坐标读偏 14px：史莱姆变骰子、蝙蝠鼻子上长肉斑、刺球额头多两个绿斑 |
| v2 | 只动瞳孔、保留眼型 | 刺球成"绿珠 + 白边"、蝙蝠左眼虹膜采样失败变深棕 |

| v4 | 从生图抠眼睛贴回换色版 | 贴片感明显：史莱姆像贴了张小眼睛贴纸 |

> **128px 蜡笔 sprite 上做局部像素重绘，必然出现贴片感。**
> 不是参数没调好，是分辨率和手绘笔触共同决定的：眼睛只有 7–12 px，
> 任何几何重建都会破坏笔触的连续性。

**最终：整只生图重画，只改眼睛。** 工具 `art/tools/ally_from_gen.py`。

生图有三条约束，缺一条就废：
1. `input_fidelity=high` + prompt 写死 "identical silhouette / identical pose"
2. 洋红底，且**动态取背景色** —— 三张生成图的底色并不一致（#E9258F / 暗玫红），写死会漏
3. 生成后**色相归位**：生图不保证落进 ally 色带（bat 出来是紫、spike 偏青 18°），
   用 `ZONES` 分区映射搬回目标带，**金银色的眼睛单独 keep 住不动**
   （整体旋转会把黄眼转成绿眼 —— 实测踩过）
4. 色相归位的判定必须**位置加权**：spike 球体中心恰好是最亮的浅绿（饱和低），
   外围橙刺反而饱和高。按"占比最大的桶"或"只看中心矩形"都会判错（前者选刺、后者选到浅绿）

**轮廓判据因此从「alpha 逐像素同」放宽到「IoU ≥ 0.95」**，实测：

| | 换色版 | 生成版 |
|---|---|---|
| slime | 1.000 | **0.988** |
| bat | 1.000 | **0.958** |
| spike | 1.000 | **0.961** |

98.6% 的轮廓重叠 —— 肉眼看是同一只，只是眼睛变了。这条写进 `duo_state.verify`，
所以**两套产线共用同一份断言**，不会出现"生成版偷偷放水"。

**两条产线怎么分工**：

| | `duo_state.py`（换色） | `ally_from_gen.py`（生图） |
|---|---|---|
| 用途 | 色系基准、快速预览、新敌人的第一版 | **入库的最终 ally** |
| 轮廓 | alpha 逐像素同 | IoU ≥ 0.95 |
| 眼睛 | 保持原样（凶） | 圆瞳 + 高光（可爱） |
| 写入 | 默认只进 `art/out/duo/hue/`，`--approve` 才进 approved | 直接进 approved |
| 何时用 | 定色系、验证新敌人的暗黑态是否落紫靛带 | 要"可爱"就必须用它 |

> **`duo_state.py` 默认不写 approved**。2026-11-27 踩过：守卫循环里跑了一次
> 无参数的 `python duo_state.py`，它把生成版 ally 覆盖回了换色版，
> 随后 `--check` 报 PASS —— 验的是被自己覆盖掉的另一个文件。**默认写库是危险的。**

### 3.2 R3 的第三条用法：同一块地，两个状态（2026-11-27 白哥定：场景的色系也要这样分类）

> **⚠️ 2026-11-27 晚：本节描述的"出两套图"已被 `§3.2.6` 的环境光 shader 取代。**
> 下面 3.2.1–3.2.5 保留为**推演记录**——里面的坑（乘法褪色、参照物选错、
> 清单外文件不被检查）在 shader 方案里同样成立，是它调参的依据。
> **新做东西一律走 §3.2.6，不要再跑 `scene_state.py --approve`。**

敌人两态表达"这只生物还病着吗"；场景两态表达"这块地归谁"。
两者在玩法上是同一件事的两半 —— `01 §3` 清完一个区域，区域变田（`03 §6`）；
玩家**必须一眼看出**"这块我清过了"，否则回访循环没有反馈。

于是同一份几何出两套色：

| | SCENE DARK 堵塞态 | SCENE ALLY 恢复态 |
|---|---|---|
| 叙事 | 导管堵了、叶绿素退了 —— 冷、湿、没有光 | 糖在流、苔在长 —— 暖木 + 苔绿 |
| 色温 | 冷像素（H150–260）**占比 ≥0.75**（实测 1.00） | 冷像素 **≤0.25**（实测 0.00） |
| 材质（土/石 → 草） | H222（深蓝家族）→ H188（冷青） | H22（土褐）→ H96（**= 蜡笔盒 11 号苔绿 #4F6B3A**） |
| 饱和上限 | **0.36**（实测 0.34） | **0.44**（实测 0.43） |
| 明度 | 0.40–0.62（实测 0.55） | 0.52–0.78（实测 0.69） |
| 几何 | **alpha 逐像素相同** | 同左 |

**两套色都落在既有蜡笔盒上**（`STYLE_LOCK §L5`）：堵塞态是 5 号深蓝、恢复态是 9 号土褐 + 11 号苔绿。
没有新造颜色 —— 这条和敌人那边"粉色不必扩第 13 色"是同一条纪律。

#### 3.2.1 判据不能照搬敌人：一块地是**多材质**的

第一版直接套用敌人的"一条色相带"（把草、土、石全搬进 82–100），跑出来是这样：

> 石砖 H24 → **H84**，一块红褐砖变成**绿砖**；石柱更糟，直接成玉雕。

根因不是参数没调好：**敌人是单一材质的生物**（史莱姆就是一身紫，一条带说得清），
**场景是多材质拼的**（草、土、石各有各的色相）。硬塞进一条带，等于把材质关系抹掉。

改成四条，全部可量：

| # | 断言 | 不做会怎样 |
|---|---|---|
| 1 | **alpha 逐像素相同** | 瓦片几何一动，拼起来就出缝（敌人那边放宽到 IoU 是因为眼睛必须重画，瓦片没这个借口） |
| 2 | **色温**：堵塞态冷像素 ≥0.75 / 恢复态 ≤0.25 | 不要求任何材质落在具体色相上，材质关系因此能保留 |
| 3 | **材质不糊**：按原图色相分区做掩膜，输出里两块还得差 ≥25° | 这就是绿砖的抓点：实测只剩 **2°** |
| 4 | 饱和 ≤0.36 / 0.44；明度落在各自区间 | 背景比演员艳，演员被吃掉 |
| 5 | 明度对比度 ≥原图 85% | 蜡笔笔触被洗平（= `§3.1.1` 那个褪色） |
| 6 | 恢复态比堵塞态亮 ≥0.08 | 「清干净了」没有画面回报 |
| 7 | **20 组演员×场景可读性**（`--matrix`） | 地换了色，站在上面的敌人没了 |

第 1–6 条由 `scene_state.py --check` 执行，第 7 条由 `--matrix` 执行。

#### 3.2.2 明度只能做加法，不能做乘法

| 做法 | 实测 |
|---|---|
| 乘法 `v×0.74` | 对比度 0.53 → **0.38（保留 72%）**，八个文件全 FAIL —— 就是 §3.1.1 的褪色换个地方复发 |
| 加法 `v−0.19` | 对比度 **分毫不动**（加常数不改差值），暗部 p5 0.45 → 0.26 仍有层次 |

乘法按比例压缩**差值**：压在亮部像"变柔"，压在暗部就是"笔触没了"。
代价也要写清：加法把整块地下移，`p1` 从 0.31 掉到 0.12 —— 最深的 1% 接近黑。
瓦片上那 1% 本来就是描边和缝，可接受；`v_range` 下限 0.40 拦着，不让自己越推越黑。

#### 3.2.3 演员可读性：参照物只能是「脚下那块」

`--matrix` 第一版拿整块瓦片的主色当参照，报出来的是**土**（占 56%），
于是纸虱（暖金 H36）被判成"和背景只差 14°，读不出"。
可实机里站着的怪物脚下是**草**（H96），土在草皮底下、被角色自己挡住 ——
**参照物选错，判据会把一个看得清的组合判死**（合成图里它清清楚楚）。
改成取「草」这个材质的输出色（`surface_hue`）。20 组结果（ΔH≥40° 或 ΔV≥0.15 且 ΔS≥0.10）：

| 演员 | 在堵塞态上 | 在恢复态上 |
|---|---|---|
| 小精灵 ally（水蓝 H206） | ΔH 18° → 靠 ΔV+0.21 / ΔS+0.16 | ΔH 110° |
| 粉翼蝠 ally（樱粉 H342） | ΔH 154° | ΔH 114° |
| 绒刺球 ally（薄荷 H147） | ΔH 39° → 靠 ΔV+0.21 / ΔS+0.13 | ΔH 54° |
| 纸虱 ally（暖金 H36） | ΔH 153° | ΔH 60°（**换参照前是 FAIL**） |
| 露珠虫 ally（水蓝 H197） | ΔH 8° → 靠 ΔV+0.28 / ΔS+0.11 | ΔH 100° |
| 五只 dark | 37–123°（绒刺球最险，靠 ΔV+0.24/ΔS+0.21） | 129–175° |

**「色相不够就靠明度+饱和」不是放水，是这套色系能成立的前提**：
场景被压在背景层（S≤0.44、V 比演员低），演员因此总有一个维度拉得开。
如果哪天场景饱和也上去了，这张表会立刻成片 FAIL —— 这正是它该干的。

#### 3.2.4 一个必须如实写的已知缺陷：底板接缝

`ground_left` / `ground_right` 与 `ground_mid` 的相邻边**并不相等**：
最大差 **141**、平均 17、144 行里只有 **7 行**相同。
`manifest.json` 里那句"右缘与 ground_mid 左缘逐像素相等"是**假的**。

真正成立的两条不变量是：`ground_mid` 左列 == 右列（自铺）、`ground_left` == `mirror(ground_right)`。
`scene_state.py --check` 只守这两条，并**每次把上面的差值打出来**，不假装它不存在。
换色是逐像素纯函数，所以接缝不会因换色而变坏 —— 但它本来就不对。

#### 3.2.5 用法

```bash
python art/tools/scene_state.py             # 候选 → art/out/scene/states/（不碰 approved）
python art/tools/scene_state.py --approve   # 确认后写进 art/approved/Terrain/
python art/tools/scene_state.py --check     # 六条断言 + 接缝（含已知缺陷）
python art/tools/scene_state.py --matrix    # 20 组演员×场景
python art/tools/scene_state.py --palette   # 两套场景色系总览
python art/tools/scene_state.py --sheet     # 四组合实机合成（场景两态 × 演员两态）
```

`*_200` 是 R4 整数缩放的派生物，**不单独出两态** —— 从基准件重新派生即可，
否则同一件事要存三份。

**摆件（`terrain_stone_block` / `pillar` / `bench` / `grass_decor`）也不出两态。**
两态回答的是「这块地现在归谁」——只有进了关卡的地面才有这个状态。摆件没进关卡，
换色就是给一个不存在的状态做资产。2026-11-27 之前 `BASE_STEMS` 把四个摆件一起收了，
于是已判定不接入的 `terrain_stone_block` 长出 `_dark` / `_ally` 并注册进 manifest，
文档说"不接入"、磁盘上却有两态 —— 两边各说各话，而且没有任何断言会抓到
（`--check` 只遍历 `BASE_STEMS`，不在清单里的文件它根本不看）。现在由
`scene_state.py --check` 的 `stray_variants()` 反向查：approved 里出现不属于地面件的
两态文件，一个都算 FAIL。

**不带后缀的基准件（`terrain_grass_top.png` 等）是"未分类的原始素材"，不是第三种态。**
它们的饱和度 0.61、明度 0.74，比绝大多数演员还艳 —— 那正是这套系统要修的东西。
prototype（`src/game.js`）目前还引用基准件，接场景两态切换时一并改掉。

#### 3.2.6 改用环境光：一份美术，两套光照（2026-11-27，替代 3.2.1–3.2.5）

白哥的原话：

> 「摆件和地面的跟色可能和敌人不太一样，我更希望是一种环境光的反馈，你明白吗？
> 就是天上有个紫色月亮造成的环境差异，这样如果行的话就不用做两套美术了。」

方向是对的，而且比"每件资产各画一套"更自洽：现在的做法是**每个材质各自换色相**，
出来的暗黑态是各转各的；环境光是**所有东西被同一束光染色**，材质关系自然保留。
顺带解决了摆件的问题 —— 灯塔、风车、石凳不用各出两张图。

**结论：地面、摆件、敌人共用一束光。敌人仍保留两套美术，但那是因为眼睛要重画
（`§3.1.4`），不是因为色系。**

**实现**：`godot/world/shaders/env_light.gdshader`（9 个 uniform）+
`art/tools/env_light.py`（同名参数、同构实现的校验端）。

##### 物理上做不到什么 —— 这条决定了整个方案

最直觉的写法是"色 × 紫光"。实测：

| 输入 | 乘紫光 (0.52,0.50,0.78) | 结果 |
|---|---|---|
| 暖黄地面 (0.72, 0.61, 0.29) | → | (0.40, 0.32, 0.23) **暗棕** |

**光只能衰减材质自身的通道。** 暖色材质里没有蓝，乘什么都不会变蓝。
这不是参数没调好 —— 真实月夜里的黄土就是暗灰褐的，不是蓝的。

所以要"紫"只能**着色**（把色相拉到月光色相上，再重定饱和/明度）。
这是风格化手法（电影调色、游戏夜景都在用），不是物理模拟；
它换来的是物理模拟给不了的东西：**所有材质共用同一束光**。

##### 明度只能加法 —— 这条第二次踩

沿用 `§3.2.2` 的结论，但这次触发点不同：**降饱和本身会削平亮度方差**
（`lum` 从"受色相影响"退化成"≈V"）。实测 `contrast_boost=1.06` 时对比度只剩 **78%**。

| contrast_boost | 1.06 | 1.15 | **1.30** | 1.38 |
|---|---|---|---|---|
| 对比度保留 | 78% | 85% | **95%** | 101% |
| 过曝像素 | 0% | 0% | **0%** | 0% |

取 1.30：拐点前最大值，且无过曝。

##### 踩到的真坑：草变粉

从黄（60°）到紫（246°）的**最短路径是负向、经过红**。土这样走没问题（一路到紫），
但植被被 `veg_protect` 减半推拉后**正好停在红/品红区间** —— 出图一看，草是粉的。

修法：植被强制走**正向**（黄→绿→青→蓝）。写进 shader 注释了，别改回单一路径：
退回最短路径，实测 33–59% 的植被落在红区。

> **中位数断言抓不到这个**：植被输出色相中位 149° 看着很健康，因为变粉的是少数
> 黄绿草尖。所以补了 `[3b]` 少数派断言：落到红/品红区 ≤8%。
> **这是本项目第四次踩"聚合指标掩盖少数派"**（前三次：空集合全称判断）。

##### 植被为什么要豁免

第一版把草也拉到紫色，出来**读不出是草**。真实月夜里植物是暗绿的（叶绿素反射为主），
不是紫的。所以 47°–162° 的黄绿—绿区要保住一部分原色相，并把降掉的饱和度补回来一些。

这条不是妥协：**环境光改的是"色温"，不是"物质"**。土石是中性材质，被染透；
植物有固有色，只染一半。

##### 六条断言（`env_light.py --check`）

| # | 断言 | 为什么是这条 |
|---|---|---|
| 1 | `night=0` 必须逐像素恒等 | 开关关掉时不许动一个像素，否则"白天"也是被加工过的 |
| 2 | 明度对比度 ≥85% | 就是褪色判据 |
| 3 | 背景饱和 ≤0.30 | 背景不许比演员艳 |
| 3b | 植被落红/品红区 ≤8% | 中位数掩盖少数派，单独数一遍 |
| 4 | 土与草输出色相差 ≥22° | 材质不糊（第一版绿砖的抓点） |
| 5 | 夜晚比白天暗 ≥0.06 | 「清干净了」要有画面回报 |
| 6 | 9 个参数在 shader 里都有同名 uniform | 两边脱钩，验的就不是游戏里跑的 |

##### 接在哪儿

`PostProcessLayer/EnvLightRect`，**排在 `DesaturateRect` 之后** ——
先变灰、再上色，紫月才照得上去。反过来写，紫色会被去色层洗掉。

`BaseRoom._setup_invasion_state()` 驱动：

| 房间状态 | `desaturate_amount` | `night` |
|---|---|---|
| 被侵占 | 1.0（灰） | **1.0（紫月）** |
| 清完 | 0.0（彩） | **0.0（日光）** |

净化时两条 tween 并行：`wipe_radius` 扩散回彩色，`night` 同步退到 0。
实机 `F3` 可手动开关，直接对比。

##### 双端校验：python 守像素，Godot 守接线

上面六条全在 `env_light.py --check` 里，它算的是**着色对不对**。
但算对了不等于**接上了**——三个房间级失效全都不报错：

| 失效 | 现象 | 为什么静默 |
|---|---|---|
| `EnvLightRect` 没挂材质 | 按 F3 毫无变化 | `mat == null` 处直接 `return` |
| 节点排到 `DesaturateRect` 前面 | 紫月看不见 | 先上色再被整层洗灰 |
| `night` 没跟侵占状态走 | 被占的房间还是日光 | 参数有名无实 |

## 4. 立体摆件：不许当"脚下的地面"，但可以当背景与竖直构件

先定状态，别把三种事混成一句"废弃"。**2026-11-27 更正过一次**，下面是更正后的：

| 件 | 状态 | 含义 |
| --- | --- | --- |
| `terrain_stone_block` / `pillar` / `grass_decor` | ✅ **接入 · 构景** | 当背景岩体、灯塔、风车、草皮点缀。**不参与碰撞形状**，不当可站立表面 |
| `terrain_stone_bench` | ✅ **接入 · 玩法** | 休息长凳的凳体（`RestBench.gd`：更新休息点 + 回满血） |
| 全部摆件的 `_dark` / `_ally` | ⬜ **暂不出** | 清区后摆件要不要跟着换色，**还没定** —— 见下面的「悬而未决」 |

> **更正记录（2026-11-27）**。上一版这里写着「石凳是唯一弃件，其余留库备用、不接入」。
> 事实是：同日并入的完整 Godot 工程里，摆件被 **15 处**正常使用（`world/rooms/Room03-05`、
> `RestBench.tscn`、`SoilPlot.tscn` 等），`RestBench.gd` 是活玩法。
> 那句判定来自 `contact_sheet.py` 的 `DECISION`（11-26 写），写的时候这门工程还没有长出来，
> 现在是**过时**而不是**错误** —— 已把 `S_DROP` 清零。判定来源依旧只有一个：
> `contact_sheet.py` 的 `DECISION`；本文只解释它。

**悬而未决：清区后摆件跟不跟色？** 地面有堵塞态/恢复态两套色（`§3.2`），
但摆件现在只有一套。Room03 的风车、Room05 的灯塔都会出现在**会被清空**的房间里 ——
地暖了、塔还是冷的，会不会突兀，需要看图决定。三条走法：
① 摆件也出两态（把 stem 加回 `scene_state.py` 的 `BASE_STEMS`，产线现成）；
② 摆件不跟色，靠"建筑不会因清区变色"这个叙事兜（要有图证明不难看）；
③ 摆件只放在不会被清的区域。**当前取 ② 未验证，等于没定。**

`Terrain/` 里的 `terrain_stone_block`（200×165 立方石）、`terrain_stone_pillar`（200×323 柱）、
`terrain_grass_decor`（200×103 草丛）都是**带顶面的 2.5D 摆件**。

**禁止的是"当可站立表面"这一种用法**，因为它有三个硬伤：

- 顶面朝向观众，角色站上去像站在斜面上，透视对不上；
- 摆件自带厚度和投影，和"照片被拍扁"的平面叙事冲突；
- 宽度 200 / 323 不是 48 的整数倍，拼不上网格，只能单件摆。

**允许的用法**（2026-11-26 修订，起因是地图要改成 X/Y 双轴）：

| 用法 | 可以吗 | 条件 |
| --- | --- | --- |
| 脚下地面 / 平台顶面 | ⛔ | 透视错，且不在网格上 |
| 背景岩体、远处山石 | ✅ | z 在玩法层之后（`z_index` 更小），不参与碰撞 |
| 竖井里的撑顶石柱 | ✅ | 当**单件**摆，不拼；吃它的"有厚度"这一点 |
| 前景遮挡（角色从后面走过） | ✅ | z 在角色之前，注意别挡住起手动作 |

所以 `asset_rules_check.py` 那条老断言（"摆件不得出现在任何场景里"）在 2026-11-27
**已经改掉**：它会把上面 15 处合法用法一并判死。现在改成**登记制**：

- 摆件的每个 `(场景文件, 摆件名)` 组合必须写进 `asset_rules_check.py` 的 `PROP_USAGE_OK`，
  并写明用途。新用法没登记就是 FAIL。
- 登记制逼着每次加摆件时回答一次"它是不是当地面"——这比自动判断靠谱：
  "挂在 StaticBody2D 下"既可能是地面误用，也可能只是场景树的组织方式（现在的
  `GrassDecor0-3` 就是后者），静态检查分不出来。
- 另有一条硬规则不看登记：**摆件出现在 `TileMapLayer` / `TileSet` 里直接算错**（那是铺格）。

新增一处摆件用法时：

1. 确认它是 `Sprite2D` / `TextureRect`（纯视觉），不是碰撞形状的来源；
2. 在 `PROP_USAGE_OK` 里登记文件 + 摆件名 + 一句用途；
3. 跑 `python art/tools/asset_rules_check.py`，看它把这条用法打印出来。

**状态只有一个真源**：`contact_sheet.py` 的 `DECISION`。本文和 `README` 都只是解释它；
两处说法打架时，以 `DECISION` 为准，然后把这里改过来 —— 别反过来。

## 5. 已知限制（如实记录，不粉饰）

1. **镜像对称一眼可见。** `mid = M + mirror(M)` 是回文，所以每 384px 能看到一次
   "对折"。试过"中间段交替翻转"来错开对称轴 —— **无效**，回文翻转后长得一样。
   真正的解法是**另画一张不对称的可平铺 384×144 中段**（新资产，走 §2.3 判据）。
   在那之前，重复感是本方案的已知代价。
2. **只有 3 种长度**（192 / 576 / 960）。要更多档位 = 再加一个尺寸的 mid。
3. **底板不能竖向堆叠。** 中间段只保证横向同边，纵向没有做同边构造，
   所以叠两层会出现横向缝。**这不是"暂时没做"，是当前这套图的几何性质决定的**，
   要竖向必须另出件（§8）。
4. **全部资产都是横版视角。** 44 张里没有一张是给竖井用的：没有侧壁、没有顶棚、
   没有阶梯、没有梯子、没有单向平台。地图要做 X/Y 双轴，这是最大的产能缺口。

## 8. 纵向（Y 轴）缺口清单：现在有 0 张

地图是 X/Y 双轴（`docs/gdd/04 §2` 五层结构里，主干与树冠都是垂直为主），
但库里 44 张全是横版视角。缺的不是"数量"，是**八个角色**——每一类对应一种关卡零件，
和横向的 `tile_cap` / `tile_mid` 一样，**先定 role 再画**。

| # | role | 建议尺寸 | 用在哪 | 判据 | 阻塞什么 |
| --- | --- | --- | --- | --- | --- |
| V1 | `wall_mid` 双向可平铺岩壁 | 96×96（2×2 TILE） | 竖井侧壁、室内墙 | **左列==右列 且 首行==末行**；体内无整行/整列透明 | 所有纵向房 |
| V2 | `wall_cap_top` 墙顶收口 | 96×48 | 竖井顶口、墙头 | 上缘收口 ≤20px；下缘==`wall_mid` 首行 | 竖井读不出"到顶了" |
| V3 | `wall_cap_bottom` 墙根 | 96×48 | 墙与地面的交接 | 同 V2 反向；上缘==`wall_mid` 末行 | 墙像插进地里失败 |
| V4 | `ledge` 附着平台 | 96×24 / 192×24 | 纵向房的落脚点 | 一侧与墙同边、另一侧收口；**有底面厚度** | 折叠门的台阶 |
| V5 | `stair` 阶梯 | 48×48 ×2 段 | 台阶（可拼 1–6 格） | 段间咬合；顶面落在网格线上 | 折叠门的"台高 4.5–6.5 格" |
| V6 | `ladder` / `vine` 梯/藤 | 48×96 | 攀爬（`ANIM` 已有 climb） | 上下同边，可无限接 | climb 状态一直没逻辑 |
| V7 | `ceiling` 顶棚 | 96×48 + 两端收口 | 室内房顶 | 横向三段，同底板语法 | 11.25 格高的房顶全空 |
| V8 | `platform_oneway` 单向平台 | 192×24 | 可上穿、下跳 | 只有上半厚度；不做底面碰撞 | 可选，不影响主线 |

**优先级**：V1→V2→V3 是**竖井的最小闭环**（没有侧壁，纵向房无从谈起）；
V4→V5 才轮到折叠门；V6 对应已有但没逻辑的 `climb`；V7 室内；V8 最后。

**产能估算**：V1 一张图 + 换色即可出整套主题（R3）；V2/V3 是同一张图的上下裁切；
V4 左右两版（镜像，R1）；V5 两段；V6 一张；V7 三段。**净增约 10 张，其中 4 张可由
已有件派生。** 这是本项目下一批美术的主线，比继续加横版件有用得多。

### 8.1 竖井的最小可玩尺寸（推算，未实测）

```
内空宽 ≥ 5 格（240px）   角色 2 格宽 + 敌人 1–2 格 + 两侧留白
内空高 ≥ 8 格（384px）   生长门阈值 7 格 + 顶部落脚 1 格
墙厚   1 格（48px）      再厚会挤掉内空
```

8 格高 × 5 格宽的竖井，一屏（11.25 格）拍不下 —— 所以**纵向房必然要纵向相机**，
`docs/gdd/04 §3` 已写"垂直房改为纵向跟随"，这次算是给它补上了资产前提。
